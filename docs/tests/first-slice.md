# 試験計画: 招待からリマインドがiPhoneに届くまで

招待から申込までとCronの送信は、手元のVoidで自動で確かめる。iPhoneのホーム画面、ロック画面への通知、端末を替えたあとのログインは、大関さんが初回配置後の本番で見る。

根拠は[設計書](../designs/first-slice.md)、[要件定義](../requirements/first-slice.md)、[API](../api.md)と[データモデル](../data-model.md)。各試験の担当は[実装計画](../implementation-plans/first-slice.md)で決める。

## 手元で試す準備

PRのCIでは型チェック、lint、Vitest、fast-check、手元のD1へのマイグレーション、Playwrightを流す。この文書では、製品の試験をこれから作るための観点を決める。
Voidの開発サーバーを使い、D1は2つとも手元に作る。Cloudflareのアカウント、AWS、Neon、実際のPush配信先にはつながない。結合検証の環境は作らない。

| 試験データ | 作り方 |
|---|---|
| 人と所属 | オーナーAとメンバーBが共有グループGに属する。別グループJ、その所属者C、アプリ未登録の認証ユーザーUを必要な試験だけに作る |
| 時刻とID | 例の時刻は日本時間。時計を固定して境目の前・ちょうど・後を作る。資源には試験用のUUIDv7を割り当てる |
| 通知先 | Bの端末B1・B2とAの端末A1を分ける。送信は試験専用の手元の受け手に差し替え、宛先、時刻、回数、中身を確かめる |
| 初回登録と復旧 | オーナーがまだいない試験は空のD1で始める。復旧では、本体だけを以前の状態に戻し、別のD1は残す |

HTTP試験は本番と同じ組み立てのHonoを通す。拒否ではHTTPの状態と`code`に加え、DBや送信に副作用がないことを見る。

## 回帰と合格の判定

APIに経路が増えたら、ログインなし・未登録・グループ外・他人のIDの試験を読み取りと書き込みの両方に足す。画面の共通処理を変えたら、ログアウト、利用者交代、通知からの復帰を再試験する。
回帰には既存のハーネスと、残した文脈の境界検査を含める。R2、Queues、解散・退会・メンバーを外す処理は、この回の動作試験の対象外とする（R21、R23、R25）。

| 受け入れ条件 | 観点 |
|---|---|
| AC-01 | X01–X02 |
| AC-02 | N01、N05 |
| AC-03 | N02 |
| AC-04 | N04–N06 |
| AC-05 | 上の要件欄でP-00〜P-10、E-01〜E-22、B-01〜B-14を照合する。ホームの次の期限・空表示はW05、通知先の帯はW06、残り時間はW03 |
| AC-06 | C04–C07 |
| AC-06a | W05 |
| AC-06b | D01–D04 |
| AC-06c、AC-07〜AC-12 | H01–H07、H09–H11 |

自動試験の受け入れ条件は、CIで通って合格とする。本番の項目は、大関さんが端末と時刻を添えて結果を残す。手元の代替Pushだけでは、iPhoneに届いたとは判断しない。
