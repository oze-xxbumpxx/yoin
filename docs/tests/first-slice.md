# 試験計画: 招待からリマインドがiPhoneに届くまで

- 前提: [要件定義](../requirements/first-slice.md)、[承認済みの設計](../designs/first-slice.md)、[実装計画](../implementation-plans/first-slice.md)、[本番配置の決まり](../decisions/ADR-0004-dev-tools.md#2026-11-24の追記)
- レベル: L3

CIでは外部サービスに接続せず、招待から受取済みまで通します。実際にメールが届くこと、ホーム画面から開くiPhoneのyoinに通知が届くこと、本番承認が権限取得より先にあることは、それぞれ実環境で確かめます。

## 試験種別と配置

| 層 | 道具・予定の置き場所 | 確かめる範囲と合格の基準 |
| --- | --- | --- |
| ドメイン・画面・外部接続の境目 | Vitest。ルートの `tests/contexts/`・`tests/functions/`、画面は `apps/web/tests/`（nodeは `*.node.test.ts`、DOMは `*.dom.test.ts`・`*.test.tsx`） | 固定時計と外部応答の代替で、状態、エラー表示、入力、認証応答と秘密の除外を確かめます。 |
| 入力を自動で変える試験 | Vitest＋fast-check。状態・時刻・送信を持つ文脈の試験に置きます | 状態遷移、予約の集合、引き受けと再送の性質が破れません。失敗時にseedと反例を残し、再現できます。 |
| DB・API | Vitest＋使い捨てPostgreSQL。 `tests/db/`・`tests/functions/` | 実際の制約・取引・同時更新とHTTPの応答を検査します。Neonにはつなぎません。 |
| ブラウザ | Playwright。 `tests/e2e/`、試験専用の代替は `tests/support/` | 2つのcontextに別の人を入れ、ランナー内のPWA・Hono・DBで通します。実メールやPushの代わりにはしません。 |
| 実環境 | オーナーが結合検証のAWS・Neon・iPhoneと、承認付きの本番配置で確認 | 結果には環境・完全SHA・担当・時刻を残します。失敗または未実施を合格に数えません。 |

現在は製品コードとVitest設定がありません。CIタスクで対象パターンを決め、上の配置が実際に検出されることを確認します。新規の公開関数・HTTPルートは、実装PRで実在する名前と試験IDの対応を添えます。

## 単体試験と性質

| 試験 | 前提・操作 | 期待する結果 |
| --- | --- | --- |
| U01 状態の決まり（AC-03、E-06） | 全状態から任意の遷移をfast-checkで試す。同じ状態も送る | 表にある遷移だけが通る。同じ状態は変更せず、禁止は `invalid_transition`。 |
| U02 時刻と予約の集合（AC-02、B-01〜B-05、P-05〜P-06） | 状態・期限・現在時刻を変え、入力を2回処理。日本時間0時台、前日20時・3時間前を過ぎた場合、12:00締切で11:58・11:59・12:00、空欄・追記・削除、受付名だけの変更を固定時計でも試す | 予約する種類と時刻の過不足がない。過ぎた予定は締切前に届く1分後だけ、締切ちょうど以降は作らない。空欄は予約せず、追記と削除を反映し、名前だけでは時刻も送信済み履歴も変えない。期限切れと受取可否は境界時刻から切り替わる。 |
| U03 再送と引き受け（AC-04、E-10〜E-13） | fast-checkで世代、引き受け、取り消し、再送、見張り、端末別結果の順を変える | 無効名や取り消し後の予約を引き受けず、同じ回を2本で送らない。新しい回は初回を含め4回まで。再送は5分後が期限前の場合だけ。見張りは10分経過前なら移し、経過後は同じ回を再開。すでに同じ回で結果を保存した端末には送らない。 |
| U04 申込と招待の入力（B-09、B-12） | 枚数0・1・99・100、受付名100字・座席と整理番号200字の境界と超過、空欄、招待期限の現在・未来7日・超過、利用数0・1・10・11を入れる | 範囲内だけ通る。文字数はUnicodeコードポイント、空欄はnull。違反は欄を示す `invalid_input`。 |
| U05 ログインと通知の画面（E-15〜E-17、F-18） | SDKの確認コード違い、期限切れ、要求上限、未確認アカウントの再開を代替。通知の許可拒否と通知先競合を再現 | コード再送・時間を置く案内・再購読を出し分ける。拒否なら設定への案内と通知先の帯を残す。原因が不明なら断定しない。 |
| U06 ホームと券（F-16、F-17、F-17a、F-18、F-25、AC-06a、B-06〜B-07） | 昨日・今日・明日の公演、自分の各状態の申込と他人の申込、期限なし、7日ちょうどと直前、通知先0台・失敗1台・回復後、座席付き申込2件を用意。明暗の12色と狭い画面で券を見る | 今日を「これから」に含め、7日ちょうどは残り時間を出さない。「次にすること」は本人の有効な期限順、帯は最初の1件だけ。空なら案内を出す。通知先があり失敗端末が0になったときだけ帯を消す。券の座席は受取済み優先、同状態は作成時刻順。編集で順を変えない。券の全指定文字が収まり、コントラストは4.5:1以上。 |
| U07 画面の共通部分（F-42〜F-45、F-48） | manifestと実ファイルを照合し、明暗を切り替える。代替APIで会員を交代し、古い要求の応答を遅らせる。同一オリジンと外部の戻り先を渡す | 名前はyoinで、180pxのApple用アイコンと192px・512pxの通常・maskableアイコンを参照できる。設計の色と書体を使う。ログアウトや会員交代で古い通信とキャッシュを残さず、遅れた応答も新しいキャッシュに入らない。アプリ内のパスだけに戻る。 |

公開する型で変更可能な値（配列・Dateなど）がある場合は、入力や返り値を試験から変更しても内部状態が変わらないことを確かめます。画面は読み込み中、空、失敗、保存後の再取得を試します。画面が先に表示を更新する場合は、失敗時に元へ戻す挙動も試します。

## DB・API・外部連携の結合試験

| 試験 | 前提・操作 | 期待する結果 |
| --- | --- | --- |

| I04 予約切替の失敗（P-04〜P-05、E-13、B-03〜B-04） | 予約を先に作ってからDB保存を失敗させる、現行予約を同時に引き受ける、送信済み期限を未来／過去へ変更、落選・削除・期限を入れ直す | 新しい組の失敗で元の期限と予約を失わない。確定後の古い名は送らない。未来なら新しい世代、過去なら予約なし。旧世代の結果を新しい表示に混ぜない。取り消しより前に引き受け済みの場合だけ届き得る。 |

| I06 締切・失敗の報告（E-10、E-12、B-01、B-05） | 12:00の締切ちょうど、途中で締切を跨ぐ、5分後が締切と同じ、一時失敗が残ったまま回数上限、C-4通知失敗、DB障害で期限まで行が残る場合を試す | 締切以降は初回・再送・見張りのどれもPushしない。途中までの受理を保持し、次の再送が無ければ対象の失敗だけを表示・報告。報告失敗時の再開はPushせず完了処理をやり直す。DBに残った行は回復期限ちょうどから完了表示となり、受理の有無を保つ。読み取りで書き換えない。 |
| I07 通知先と再起動（E-15、F-18） | 同じendpointを本人が再登録、他人が登録、許可し直し、端末の再送成功 | 本人は重複せず、他人には既存IDを返さず409。購読を作り直せる。成功した端末の失敗時刻だけを消し、他人の購読を返さない。 |
| I08 配置の検査（F-02、AC-06） | 代替の配置履歴で起動時と実配置のSHAが違う場合、履歴の不一致・取得失敗・順序不明、初回を試す | 環境別の公開設定と固定した成果物を使う。承認SHAが結合検証の最新成功と違うか取得不能、本番の成功より古いか順序不明なら権限取得前に停止。本番の履歴を読めた0件かつオーナー確認済みの初回だけ例外。 |
| I09 入金済みから受取済み（P-06、P-08） | 当選の申込に、入金期限の前日20時と締切の3時間前の予約が2件あり、どちらも未送信であることを確かめる。未来の受取開始日時を用意し、申込者が入金済み、受取済みの順に変える | 入金済みにした直後に、入金期限の予約2件が両方とも無効になり、受取開始の通知が予約される。受取済みにすると、有効な予約が残らない。 |
| I10 環境の定義（F-01、F-04） | 両環境のTerraform定義と初回準備が定めた状態・権限を照合する | 状態と権限は環境ごとに分かれ、CIには初回用の状態へのアクセスを許さない。共有のSES抑止と警報は二重に管理しない。 |
| I11 作成と削除の再送（E-08） | 共有アーティスト・会場、下書きの作成を同じIDと同じ／違う中身で再送する。別のメンバー・別グループからの再送と削除後の再送も試す | 同じ作成は201の後に200で1行。共有資源には同じグループの別メンバーも同じ入力で再送できる。別グループ、違う入力、他人の非公開下書きのIDは汎用409。同じ名前で別IDのアーティストは `already_exists`。削除後は副作用を増やさず404。 |

### 公開する入口の網羅と回帰

AC-05では、下の対応だけでなく、要件の正常系・異常系・境界条件の各IDとホームの指定された表示に試験があることを照合します。

| 設計で公開する入口 | 対応 |
| --- | --- |
| 自分・所属・グループ・メンバー、招待発行・表示・受諾、登録前Lambda、初期データ | I01、E2E-01 |
| アーティスト・会場、下書きの一覧・作成・編集・削除・確定、公演の一覧・詳細 | U06、I02、I11、E2E-01 |
| 申込の一覧・詳細・作成・編集・削除・状態変更 | U01〜U04、I02〜I06、I09、E2E-01 |
| 通知先の一覧・登録、通知送信Lambda、通知を押したときの画面遷移 | U03、U05、I04〜I07、I09、E2E-02、M02〜M05、M08 |
| 共通の画面・通信、ログイン状態の境目 | U07、E2E-02、M01、M04 |
| DB適用、配置、PWA設定、承認前後の権限取得 | I03、I08、I10、D01〜D04 |

初回なので既存製品の回帰試験はありません。以降のPRでは招待と権限、申込と通知、デプロイと試験認証の排除を繰り返し確かめます。範囲外の解散・退会、手動再送、分配の試験は追加しません。

## Playwrightの2人と試験データ

| 試験 | 前提と操作 | 合格の基準 |
| --- | --- | --- |
| E2E-01 2人の参加から受取（AC-01、P-01、P-03〜P-06、P-08〜P-09） | ランナーが初期データでオーナーと共有グループを作る。別々のcontextと試験JWTで、オーナーの招待発行 → 2人目の参加 → 公演確定 → 申込 → 当選 → 入金済み → 受取済みを通す | 2人目の申込はオーナーにも読めるが編集操作は出ない。申込の変更や状態の再読込で表示が崩れない。 |
| E2E-02 通知からの移動と会員交代（P-07、E-09、B-11） | 試験の通知先URLを使い、ログインあり・なし、消した申込、同じブラウザで会員を交代して開く | ログイン後は元の申込へ戻る。不在は見つからない表示。旧会員の下書きや通知状態を一瞬も見せない。 |

試験専用の入口で短命な鍵と試験issuerを使い、代替アダプターがJWTを検証してからHonoへ渡します。本番成果物に試験の入口・鍵・発行者がなく、試験JWTでは使えないことをCIで別に検査します。時計・招待・期限・Push応答はランナーで用意し、実際の利用者データは使いません。

| 試験 | 要るデータと作る人 | 操作と合格の基準 |
| --- | --- | --- |
| M01 招待とPWA追加（AC-07、P-01〜P-02） | 初期データがオーナーと共有グループを作る。オーナーが招待を発行し、2人目用に別の検証宛先を用意 | iPhone Safariで招待を開いて参加。ホーム画面にyoinを追加し、そこから再ログインして通知を許可する。通知先が登録され、帯が消える。 |
| M02 結果発表と通知を押す動作（AC-08、AC-10、P-04、P-07） | オーナーが2人目として公演と数分後の結果発表を持つ申込を作る | ロック画面に公演名と受付名つきで届く。押すとその申込を開く。 |
| M03 入金期限（AC-09、P-05） | オーナーが2人目として、前日20時を過ぎた時刻に、3時間と数分後に締め切る当選の申込を作る | 前日20時の分は登録の1分後、3時間前の分はその予約で起動する。予定時刻は固定時計の試験で厳密に比較する。 |
| M04 受取開始とログアウト（AC-10a、AC-10b、P-06） | オーナーが2人目として受取開始が数分後の入金済み申込を2件作る | 1件目で受取開始の着信を確認。2件目は予約後にS-22でログアウトし、通知先を残す。通知を押して同じ人で再ログインし、ホームでなく押した申込へ戻る。 |
| M05 別の人から見た申込と明暗（AC-11、AC-12、P-09） | M02〜M04の申込。大関さんはパソコンでオーナーとしてログインし、iPhoneは2人目の利用者として開く | パソコンで読めるが編集できない。iPhoneは端末の明暗設定で切り替わる。 |
| M06 認証とSES | オーナーが検証専用のGmail・iCloud宛先、正常・無効な招待を用意する。結合検証から本番と同じyoin専用の送信元で認証メールを送る | 無効な登録はAdminGetUserで不在・メール0通、正常な登録確認は1通、再ログインはメールOTP。休止したNeonで登録の応答時間を測り、開始枠超過で新規メールが出ず既存ログインは継続。認証メールはGmail・iCloudの両方で受信トレイに入る。片方でも迷惑メールに入るか、届かなければ不合格。実送信は1日10通までで1秒より間隔を空ける。 |
| M07 失敗キュー・SES設定・Gateway | オーナーがSchedulerとLambdaの失敗を各1件用意し、結合検証の承認済み構成だけを使用 | 欠測を異常にしない設定を確認し、各試験前に対象キューを空にして警報OKを待つ。経路ごとの失敗メッセージとALARM・メールを別に確認。SES抑止設定は `BOUNCE` と `COMPLAINT` の2つ。バウンス等はSESシミュレーター、抑止と解除は同意済みの検証宛先で別試験。JWTなし・別issuer・別clientをGatewayで拒否。 |
| M08 移した見張りの設定（U03の実環境確認） | オーナーが結合検証で、通知送信を引き受けてから10分未満の試験データを用意する。見張りを起動して予約を移し、移す前後のScheduler設定を読む | 同じ名前の見張りが引き受けから10分1秒後に移る。ターゲット、実行ロール、入力、失敗キュー、再試行の設定、`FlexibleTimeWindow=OFF`、自動削除なしが保たれる。 |
| M09 初回状態の移行と権限 | オーナーがAWS・Neonの対象環境とSSMの値を用意し、Macで作った初回状態をS3に移す | 移行先から状態を読め、Terraformのplanに意図しない差分がない。CIロールでは初回用キーを読み書きできない。秘密と状態をログに載せない。 |
| M10 配置と監視の設定 | CIが完全SHA付きの成果物を作り、オーナーが両環境の配置結果を読む。本番は承認後に読む | LambdaのSHAと時刻のタグが配置と合い、警報・流量・ログ保持が設計どおり。共有資源を二重に管理していない。 |

オーナーは通知ごとに、予約時刻（FlexibleTimeWindowなし）、Schedulerの起動、Push受理、iPhone着信を別々に残します。通信できる端末で、通常経路の目安は起動が予約の分内（60秒未満）、受理が起動から60秒以内、着信が受理から2分以内です。範囲を外れた段を切り分け、着信の欠落を成功にしません。記録に名前・メールアドレス・トークン・購読URLを載せません。

## 最初の実デプロイと承認
