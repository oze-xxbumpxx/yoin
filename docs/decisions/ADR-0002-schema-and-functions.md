# ADR-0002スキーマとLambdaの分け方

- 状態：提案（2026-11-06。2026-11-07にレビューの指摘と、ユーザーストーリーで決まった「メンバーを外す・抜ける」を反映）
- 決めた人：大関
- 関連：[ADR-0001](ADR-0001-bounded-contexts.md)、[データモデル](../data-model.md)、[文脈マップ](../context-map.md)

## 背景

ADR-0001で、yoinを6つの文脈（グループ、公演カタログ、参戦記録、チケット、グッズ、通知）に分けた。そこでは、データベースのスキーマ、Lambdaの関数、コードの置き場所の分け方を決めなかった。

工程3でデータモデルを作り、テーブルは28になった。文脈の境目をデータベースとデプロイのどこまで反映するかを決める必要がある。前提は次のとおり。

- 利用者は1年後に10人以下。費用はAWSとNeonの無料枠に収めることを目指す。
- データベースはNeon（Postgres）。
- リマインドは、期限の種類ごとに決めた時刻にWeb Pushで送る。
- 解散と退会は、1つの処理が文脈を順に呼ぶ（ADR-0001）。

2026-11-07に、この提案をほかのAIにレビューしてもらい、承認前に直すべき点が10件見つかった。グループをまたぐ参照、解散・退会の途中の書き込み、途中で止まった削除の再開、退会の完了条件、通知の取り消し、解散で残す参戦の範囲などである。決定の3、5、6はその指摘を受けて足し、2と4は変えた。

## 決定

### 1. Neonの1つのデータベースに、文脈ごとのスキーマを作る

| 文脈 | スキーマ | テーブル数 |
|---|---|---|
| グループ | `groups` | 5 |
| 公演カタログ | `catalog` | 8 |
| 参戦記録 | `attendance` | 4 |
| チケット | `ticket` | 2 |
| グッズ | `merch` | 6 |
| 通知 | `notification` | 3 |

スキーマ名はモジュール名と同じにする。ただし`group`はSQLの予約語なので、スキーマ名だけ`groups`にする。モジュール名は`group`のまま。

### 2.外部キーは、動きを決めて張る

- 同じスキーマの中は、親に従う行（セトリ、参戦記録など）にCASCADE、使い回す参照先（会場、ツアー、オーナーなど）にRESTRICTを付ける。外部キーごとの一覧はデータモデルに書く。
- 同じスキーマの中で別の行を指すときは、所属を含む複合外部キー（`(group_id, venue_id)`など）にし、別グループの行を結べないようにする。
- 文脈をまたぐID（公演ID、ツアーID、グループID、ユーザーID）には、RESTRICTの外部キーだけを張る。CASCADEは使わない。消す順番は解散・退会の処理が決め、順番を間違えたときや孤児の行ができそうなときにDBが断る。
- マイグレーションはgroups → catalog → ほかの順に流す。

### 3.書き込みは、グループの文脈のロックを通す

- 書き込みはすべて1つのDBトランザクションで行う。最初にグループの文脈の公開関数で、グループ、操作した人、そのメンバーの行が有効かを確かめ、その行を`FOR SHARE`でロックする。
- 解散、退会、メンバーを外す・抜けるの開始は、同じ行の状態を更新する。実行中の書き込みが終わってから状態が変わり、そのあとの書き込みは断られる。
- 各文脈の公開関数は「操作した人」と「グループID」を受け取り、対象の行と指定されたIDがすべて同じグループのものかを確かめる。操作した人のIDはJWTから取る。
- このため、LambdaからNeonへの接続は、トランザクションの途中で判断を挟める方式にする。

### 4.ほかの文脈がメンバーを指すときは、ユーザーIDとグループIDで持つ

ADR-0001の「メンバーIDをそのまま使う」を改める。参戦は解散後も本人に残るので、解散で消えるメンバーの行ではなくユーザーを指す必要がある。退会のときも、本人のデータをユーザーIDでまとめて消せる。メンバーかどうかの確認は、今までどおりグループの文脈に聞く。

### 5. Lambdaの関数は3つにする

| 関数 | 起動するもの | 受け持つこと |
|---|---|---|
| `api` | API GatewayのHTTP API | 画面からのすべての操作。解散、退会、メンバーを外す・抜けるは、受け付けて記録するところまで |
| `erasure-worker` | `api`からの非同期の起動と、止まったときに再開させるEventBridge Schedulerの1回限りの予約 | 解散、退会、メンバーを外す・抜けるの処理。`groups.erasure_jobs`を読み、止まったところから続ける |
| `notification-sender` | リマインド1件ごとのEventBridge Schedulerの1回限りの予約 | その予約のリマインドを引き受け、Web Pushで送る |

`api`の中は、文脈ごとのディレクトリに分ける。解散と退会を専用の関数に分けるのは、HTTP APIが30秒で応答を打ち切ることと、退会した本人は画面を開けず、続きを呼ぶ人がいないためである。通知の送信は、起動のされ方、実行時間、必要な権限が画面の操作と違うので、別の関数にする。

どの関数も定期的には起動しない。リマインドは1件ずつ1回限りの予約を作り、解散・退会・外すは止まったときだけ動く見張りの予約を作る（2026-11-07）。定期的にNeonへ問い合わせると、そのたびに休んでいるNeonが起き、無料プランの計算時間を使い切るおそれがあるためである。予約の作り方は[データモデル](../data-model.md)に書く。

### 6.解散、退会、メンバーを外す・抜けるは、途中から再開できるように作る

- 進み具合を`groups.erasure_jobs`に保存し、段階ごとに進める。メンバーを外すのと自分から抜けるのは、同じ処理（種類`leave`）で、その人のそのグループでのデータだけを扱う。
- DBだけで済む処理は1つのトランザクションにまとめる。S3の画像は、消す予定のキーを`merch.object_deletions`に書いてから消す。
- 退会は、状態を変える → Cognitoでサインアウトさせて無効にする → アプリのデータを消す → Cognitoのアカウントを消す → `users`の行を消す、の順にする。APIは`users`の行が有効かを毎回確かめる。

### 7.コードの置き場所

```
src/
  contexts/
    group/          グループ（スキーマは groups）
    catalog/        公演カタログ
    attendance/     参戦記録
    ticket/         チケット
    merch/          グッズ
    notification/   通知
  usecases/
    disband-group/  解散の処理
    withdraw-user/  退会の処理
  functions/
    api/                  関数 api の入口
    erasure-worker/       関数 erasure-worker の入口
    notification-sender/  関数 notification-sender の入口
```

- 文脈のディレクトリの外からは、その文脈が公開した関数だけを使う。ほかの文脈のスキーマのテーブルは、SQLでも直接読まない。
- 複数の文脈から集めて画面に出す処理は、`functions/api`の中で各文脈の公開関数を呼んで組み立てる。

## 検討した案

### 文脈ごとに別のデータベースにする

境目はいちばんはっきりする。ただし、接続先と認証情報が6つになり、マイグレーションも6系統になる。決定3のロックも、1つのトランザクションでは書けなくなる。採らない。

### スキーマを分けず、1つのスキーマにテーブルを並べる

最も単純である。ただし、どのテーブルがどの文脈のものかが名前の付け方だけになり、ほかの文脈のテーブルを読むコードを書いても気づきにくい。公演カタログとグッズの両方にある`drafts`も、名前を変える必要が出る。採らない。

### 文脈をまたぐIDに外部キーを張らない

2026-11-06にはこの案を採った。CASCADEだと、公演を消したときに参戦も消え、写しを取る前に記録が失われるためだった。レビューで、RESTRICTなら消える順番を決めず、間違った順番を断るだけだとわかった。解散の順番はもともとRESTRICTを満たす。1つのDBなので張る手間も小さい。2026-11-07に決定2へ変えた。

### メンバーIDで指す

ADR-0001の書き方どおりになる。ただし、解散のときに参戦の持ち主をメンバーからユーザーへ付け替える処理が要り、退会でもメンバーの行を経由して本人のデータを探すことになる。採らない。

### 文脈ごとにLambdaの関数を分ける

文脈ごとにデプロイと権限を分けられる。ただし、関数、設定、ログが6倍になり、解散と退会のように文脈をまたぐ処理を置く場所に困る。コールドスタートも関数の数だけ起きる。採らない。

### 関数を2つにし、解散と退会を`api`の中で動かす

2026-11-06にはこの案を採った。レビューで、HTTP APIの30秒の打ち切りと、退会した本人が続きを呼べないことが指摘された。画面から少しずつ続きを呼ぶ形にしても、退会では呼ぶ人がいない。2026-11-07に決定5へ変えた。

### 送信の関数を15分ごとに起動して、まとめて送る

予約の作成と削除が要らず、作りは単純になる。ただし、起動のたびにNeonに問い合わせるので、休んでいるNeonが月に数千回起きる。Neonは問い合わせのあと数分動き続けるので、無料プランの計算時間の上限に近づくか超えるおそれがある（推測。工程6で確かめる）。2026-11-07に、1件ずつ予約する形を選んだ。

### 通知の送信も含めて1つの関数にする

関数は1つで済む。ただし、Schedulerからの起動と画面からの操作が同じ入口に混ざり、タイムアウトと権限を分けられない。採らない。

## 結果

### よくなること

- スキーマ名を見れば、どのテーブルがどの文脈のものかがわかる。ADR-0001の文脈がデータベースでもそのまま見える。
- 別グループの行を結ぶこと、解散・退会の途中の書き込みで孤児の行が残ることを、ロックと外部キーの両方で防げる。
- 解散と退会の順番を、コードの1か所（`usecases`）で読める。途中で止まっても、誰も画面を開かずに最後まで進む。
- あとで文脈を別の関数に切り出すときも、ディレクトリとスキーマの境目がそのまま使える。

### 引き受けること

- 文脈をまたぐ外部キーがあるので、マイグレーションの順番を守る必要がある。
- 書き込みのたびにグループとユーザーの行をロックする。利用者が10人以下なので、待ちが問題になることはない見込みである。
- 途中で判断を挟めるトランザクションが要るので、Neonへの接続の道具が限られる。
- ほかの文脈のテーブルを読んでいないかは、レビューと検査の道具で見る必要がある（道具は工程4で決める）。
- 関数が3つになり、IaCの定義が増える。

## この決定では決めないこと

- ORMとマイグレーションの道具、LambdaからNeonへの接続の道具（工程4）
- 文脈の境目を守るための検査の道具（工程4）
- Neonの無料プランの計算時間と、Schedulerの予約の数が料金の範囲に収まるか（工程6で公式の料金で確かめる）
- 自動入力（MVP2）を`api`に入れるか、別の関数にするか（MVP2）

なお、入金期限を過ぎた申込の「期限切れ」は保存せずに計算するので、そのための関数や定期の処理は置かない（[データモデル](../data-model.md) R9）。
