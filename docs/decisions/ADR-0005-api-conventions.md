- 関連：[API設計](../api.md)、[ADR-0002](ADR-0002-schema-and-functions.md)、[ADR-0003](ADR-0003-layers-in-contexts.md)、[ADR-0004](ADR-0004-dev-tools.md)、[データモデル](../data-model.md)、[論点の記録](../discussions/api-design.md)

## 背景

実装は土台も含めてDevinに渡し、画面とLambda `api`を別のタスクで作る（`AGENTS.md`）。両方のタスクが同じ前提で書けるように、すべてのAPIに共通する形を委譲の前に決める。

決める前からあった前提は次のとおり。

- 公開関数は「操作した人」と「グループID」を受け取り、書き込みは最初にグループの行を`FOR SHARE`でロックする（ADR-0002の決定3、データモデル「グループの所属と権限」）。
- 別グループのIDを指定されたら、存在しないときと同じ「見つからない」を返す（同上）。
- 入力と出力の型はZodと`hono/client`で画面と共有し、OpenAPIは作らない（ADR-0004の追記、2026-11-21）。
- IDはUUIDv7をアプリで作る（データモデル「全体の決まり」）。
- 公演会場の近くでは電波が弱く、返事が届かずに送り直すことがある。オフライン対応はしない（PR/FAQ）。

## 決定

### 1.工程5で、画面の一覧と移り方、画面ごとに呼ぶAPIまで決める

画面は23にし、移り方と呼ぶAPIを[API設計](../api.md)に書く。MVP1のユーザーストーリー37本を、どれかの画面とAPIに結びつける。見た目（色・配置・文言）は最初の1本の設計で決める。

Devinに画面のタスクを分けて渡すには、画面とAPIの対応が要る。見た目は、動くもので確かめるほうが早い。

### 2.グループの中の資源は、パスの先頭にグループIDを置く

`/groups/{groupId}/concerts/{concertId}`の形にする。パスのグループIDとJWTのユーザーを公開関数にそのまま渡し、そのIDでロックを取る。グループをまたぐもの（自分の参戦の一覧、通知先、退会）は`/me/...`に置く。

ロックを取る前にグループIDが決まるので、ほかの文脈の表を先に読まずに済む。どの要求がどのグループのものかがパスだけでわかり、ログと試験でも追いやすい。

### 3.作成は画面がUUIDv7のIDを作って送り、2回目は1回目の結果を返す

- 同じIDの行が同じグループにあって中身も同じなら、1回目と同じ応答を200で返す。
- 中身が違うときと、別グループの行と重なるときは`id_conflict`で断り、行の中身は返さない。
- 作成のほかの操作は、2回送っても結果が同じになる形にする。状態を進める操作は「どの状態にするか」を送り、一覧の置き換えは`PUT`にする。

要求ごとの記録の表を増やさずに、申込や頼まれ物が2つできることを防げる。

### 4.エラーはRFC 9457の形に`code`を足して返す

`application/problem+json`で返し、`code`（`not_found`・`invalid_input`・`stale_version`・`group_closing`など）を足す。入力の誤りでは、欄ごとの理由を`errors`に入れる。`code`の一覧は[API設計](../api.md)の「エラーの形」にある。

決まった形を使えば、形の説明を自分で書かずに済み、決めるのは`code`の一覧だけになる。

### 5.仮に決めて、承認までに異議がなければ確定するもの

- 一覧のAPIはページを分けない。公演と参戦の一覧は年で絞れる。
- 同時に直したときの上書きを防ぐのは、セトリだけにする（版番号）。
- 画面はAPI GatewayのURLへ直接送り、CORSは画面のドメインだけを許す。
- すべてのパスでCognitoのJWTを求める。招待を見るAPIと招待から参加するAPIの2本だけは、`users`の行が無いJWTも受ける。JWTの要らないパスが無く、招待リンクを通らずにユーザーを作らない決まり（データモデル「退会の手順」）もそのまま守れる。これはClaudeが案として決めた。
- 最初のオーナーはAPIで作らず、デプロイの流れで流す初期データの手順で作る。手で流す手順を作らない決まり（`AGENTS.md`）に合い、E2Eのデータも同じ方法で作れる。
- 招待リンクのトークンは、SSMに置く秘密の値とリンクのIDからHMAC-SHA256で作る。発行の要求を送り直しても同じトークンを返せ、トークンの強さを画面の乱数に頼らずに済む。

## 検討した案

論点ごとの利点と欠点は[論点の記録](../discussions/api-design.md)にある。

### 決定1について

- APIだけ決め、画面は最初の1本で決める。工程5は早く閉じるが、画面を描いたときにAPIの足りない項目が見つかって戻る。
- 主要な画面のHTMLの見本まで作る。見た目まで先に確かめられるが、工程が延び、見た目は実装で変わることが多い。

### 決定2について

- グループIDをヘッダで送る。パスは短いが、付け忘れた要求を見落としやすく、ログで区別しにくい。
- パスに入れず、資源のIDからグループを引く。画面はグループIDを知らなくてよいが、ロックの前にほかの文脈の表を読むことになる。

### 決定3について

- 要求ごとに`Idempotency-Key`を付け、結果を別の表に24時間残す。作成以外にも使えるが、表と古い記録を消す処理が増える。
- 何もしない。作りは単純だが、リマインドの重複や合計金額のずれを利用者が気づくまで直せない。

### 決定4について

- `{ "error": { "code", "message", "fields" } }`の独自の形。小さいが、形の説明をAPI設計に自分で書く必要がある。

### 決定5の招待について

- 招待を見るAPIだけJWTなしで開ける。ログイン前にグループ名を見せられるが、JWTの要らないパスがひとつ増え、トークンを総当たりされる経路になる。

## 結果

### よくなること

- 画面とLambdaのタスクを、画面とAPIの表を見て分けられる。
- どの作成も、送り直しで2つできない。
- 画面はエラーの`code`だけを見て文言を出し分けられる。

### 引き受けること

- 作成のAPIはどれも、IDが重なったときの比べ方（中身が同じか）を実装と試験で持つ。
- 公演の下書きの確定と品目の下書きの確定は、下書きが消えたあとの送り直しでも結果を返せるように、作る行のIDを要求に入れる。
- 招待リンクのトークンを作る秘密の値が、SSMに1つ増える。値を替えると、まだ使われていない招待リンクはすべて使えなくなる。
- 2本の要求が重なったときのために、作成は`INSERT ... ON CONFLICT DO NOTHING`で書いて読み直し、招待リンク・下書き・申込の行は`FOR UPDATE`で取る。
- 版の番号をパスに付けないので、互換を壊す変更では、古い画面からの要求を受ける期間をその変更の設計書に書く。

## この決定では決めないこと

- ログインの方式（最初の1本の要件）
- 見た目、画面のルーティングとデータの取り方の道具（最初の1本の設計）
- API Gatewayの流量の制限の値（工程6）
