# ADR-0003文脈の中の層の分け方

- 状態：承認（2026-11-17、PR #7のマージ）。層の数（決定1）は2026-11-17に大関が選んだ
- 決めた人：大関
- 関連：[ADR-0001](ADR-0001-bounded-contexts.md)、[ADR-0002](ADR-0002-schema-and-functions.md)、[論点の記録](../discussions/code-layers.md)

## 背景

ADR-0001でyoinを6つの文脈に分け、参戦記録・チケット・グッズをコアの文脈にした。ADR-0002では、文脈ごとのディレクトリ（`src/contexts/<文脈>/`）と、文脈の外からは公開関数だけを使う決まりを決めた。どちらも、文脈の中のコードをどう分けるかは決めていない。

実装は最初からDevinに委譲する（`AGENTS.md`）。委譲の前に、ファイルをどこに置き、何が何に依存してよいかを決めておかないと、タスクごとに形がばらばらになる。ORMや境目の検査の道具（工程4）を選ぶにも、この形が前提になる。

前提は次のとおり。

- 書き込みはすべて1つのDBトランザクションで行い、最初にグループの文脈の公開関数で`FOR SHARE`のロックを取る（ADR-0002の決定3）。ほかの文脈の公開関数も、同じトランザクションの中で呼ばれる。
- 解散・退会・抜けるは、`src/usecases/`の処理が文脈を順に呼ぶ（ADR-0001、ADR-0002）。
- yoinはポートフォリオとして、Cookpit・tomotabiにない技術要素を見せる（PR/FAQ）。

## 決定

### 1.文脈ごとに層の数を変える

コアの文脈（`attendance`・`ticket`・`merch`）は3つの層に分ける。

```
src/contexts/ticket/
  domain/          エンティティ・値オブジェクト・状態の移り方。DBもAWSも知らない
  application/     公開関数（ユースケース）。domainを使い、リポジトリのインターフェースを呼ぶ
  infrastructure/  リポジトリの実装（SQL）、S3やSchedulerの呼び出し
  index.ts         文脈の外に見せる公開関数だけを出す
```

コアでない文脈（`group`・`catalog`・`notification`）は、`application/`と`infrastructure/`の2つにする。決まりは公開関数の中に書き、`domain/`は作らない。

- チケットの申込の状態の移り方、参戦記録の同行者の決まり、グッズの頼まれ物と購入担当の決まりは、DBなしの単体試験で確かめたい。コアの文脈に`domain/`を置くのはこのためである。
- 公演カタログや通知は、ほとんどが登録・一覧・予約の作成で、守る決まりが少ない。3層にすると、中身のないクラスが増える。
- グループの文脈はロックと認可の窓口だが、決まり（オーナー、メンバーの状態）は少ないので2層にする。決まりが増えたら、その文脈だけ3層にしてよい。

### 2.依存の向きを1つにする

- `functions/`（Lambdaの入口）→ `usecases/` → 各文脈の`index.ts`（公開関数）の順に呼ぶ。
- 文脈の中では、`application/` → `domain/`の向きにだけ依存する。`domain/`は外部のライブラリ、DB、AWSのSDKをimportしない。
- `infrastructure/`は、`application/`か`domain/`に置いたインターフェースを実装する。`application/`から`infrastructure/`を直接importしない。
- 実装の組み立ては、各Lambdaの入口で手書きする。DIコンテナは使わない。関数が3つで、組み立てる部品が少ないため。

### 3.トランザクションは入口で1つ開いて渡す

- 1回の要求につき、Lambdaの入口がトランザクションを1つ開き、公開関数に引数で渡す（Unit of Work）。公開関数は自分でトランザクションを開かない。
- ほかの文脈の公開関数を呼ぶときも、同じトランザクションを渡す。グループの文脈のロック（ADR-0002の決定3）は、最初の呼び出しで取る。
- `erasure-worker`は、`erasure_jobs.step`の1段階ごとに1つのトランザクションにする（データモデル「解散と退会の進め方」）。
- `erasure-worker`は、画面の操作と同じ確かめ方を使わない。画面の操作は「グループ・ユーザー・メンバーが`active`か」を確かめるので、`disbanding` / `withdrawing` / `leaving`になった後の削除まで断ってしまう。代わりに、グループの文脈が削除ジョブ用の公開関数を別に出す。この関数は`erasure_jobs`の行を`FOR UPDATE`でロックし、行が`running`であること、対象のグループ・ユーザー・メンバーがジョブの種類に合った処理中の状態であることを確かめる。操作した人はJWTではなく、記録済みのジョブを根拠にする。非同期の起動と見張りの予約が重なって2つの`erasure-worker`が動いても、ジョブの行のロックで1つずつ進む。

### 4.取り消せない外部の操作は、コミットのあとに行う

トランザクションを入口で開くので、公開関数の中でSchedulerやS3を呼ぶと、DBの変更が巻き戻っても外部の操作は残る。そこで、外部の操作をいつ行うかを次のように分ける。

- 消す操作（Schedulerの予約の削除、S3の削除）は、コミットのあとに行う。公開関数は、コミット後に行う操作をUnit of Workに登録するだけにし、入口がコミットに成功してから実行する。実行は`infrastructure/`が受け持つ。失敗しても、DBが正しければ困らない形にする（予約が起動しても行が`canceled`なので送らない。S3は`object_deletions`に残ったキーを次の回に消す）。
- 作る操作（Schedulerの新規予約と時刻変更用の別世代の予約、S3の中のコピー）は、コミットの前に行ってよい。コミットが失敗して外部にだけ残っても、予約は起動したときにDBに有効な名前の行がないので何も送らず、画像は解散・退会・抜けるで接頭辞ごと消える（データモデルR11・R13）。
- 例えば入金済みにするときは、受取開始の予約を作り、DBで入金期限の予約を`canceled`にしてコミットし、そのあと入金期限のSchedulerの予約を消す。コミットが失敗すれば、入金期限の予約は消えずに残り、受取開始の予約は行がないので何も送らない。
- `erasure-worker`のCognitoの操作（サインアウトとアカウントの削除）は、それだけで1つの段階にする。外部の操作が成功してから、次のトランザクションで`step`を進める。外部の操作は、2回呼んでも結果が変わらない形で呼ぶ。

### 5.境目を機械で確かめる

次の2つを、CIで検査する。道具は工程4で選ぶ。

- 文脈の外から、その文脈の`index.ts`以外をimportしていない。
- `domain/`が、`infrastructure/`・外部のライブラリ・AWSのSDKをimportしていない。

## 検討した案

### 6つの文脈をすべて3層にする

形がそろい、Devinに渡す説明は1つで済む。しかし、公演カタログや通知には守る決まりが少なく、`domain/`に中身のないクラスが並ぶ。試験も、DBを使う結合試験で足りる部分が多い。詳しくは[論点の記録](../discussions/code-layers.md)。

### すべての文脈を2層にする（公開関数にSQLと決まりを書く）

ファイルが少なく、最初は速く書ける。しかし、チケットの状態の移り方や同行者の決まりをDBなしで試験できず、コアの決まりがSQLの近くに散らばる。ポートフォリオとして見せたい「ドメインの決まりを分けて試験する」形にもならない。

### 公開関数がそれぞれトランザクションを開く

呼ぶ側の作りは簡単になる。しかし、グループの文脈のロックと、ほかの文脈の書き込みが別のトランザクションになり、ADR-0002の決定3（解散・退会と書き込みを順番に並べる）が守れない。

### DIコンテナを使う

部品の差し替えが楽になる。しかし、Lambdaは3つで部品が少なく、コンテナの設定と起動時間のほうが重い。

## 結果

### よくなること

- コアの決まりを、DBなしの単体試験で速く確かめられる。
- Devinに渡すタスクで、ファイルの置き場所と依存してよい先が決まっている。境目の検査がCIで止めるので、レビューで見る量が減る。
- 1回の要求が1つのトランザクションに収まり、ロックの決まり（ADR-0002）とそろう。

### 引き受けること

- 文脈によって層の数が違うので、Devinへの説明とレビューでは、どちらの形かを文脈ごとに示す必要がある。
- 公開関数はすべてトランザクションを引数に取るので、関数の引数が1つ増える。
- Unit of Workに、コミット後に行う操作を登録する仕組みが要る。コミット後の操作が失敗しても困らないかを、外部の操作ごとにレビューで確かめる。
- コアでない文脈に決まりが増えたときは、3層に移す作業が要る。

## この決定では決めないこと

- 言語とORM、マイグレーションの道具、Neonへの接続の道具（工程4）
- 境目の検査の道具（工程4）
- 画面（PWA）のコードの分け方（工程4以降）
