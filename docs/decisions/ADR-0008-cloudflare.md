# ADR-0008 インフラとDBをCloudflareに移し、Voidで組む

- 関連：[アーキテクチャ](../architecture.md)、[論点の記録](../discussions/cloudflare-migration.md)、[ADR-0002](ADR-0002-schema-and-functions.md)、[ADR-0004](ADR-0004-dev-tools.md)、[ADR-0006](ADR-0006-region-and-cost.md)、[ADR-0007](ADR-0007-cognito-email.md)
- 置き換えるもの：ADR-0002の決定1・決定3・決定5、ADR-0004の決定3・決定4・決定5・決定7・決定8の一部と2026-11-21・2026-11-25の追記の一部、ADR-0006の決定1〜7、ADR-0007の全部。置き換えた決定は、各ADRの末尾の追記に書いた

## 背景

2026-11-27に大関から、インフラとDBをCloudflareでまとめて管理したいと相談があった。いまの設計はAWS（Lambda、API Gateway、EventBridge Scheduler、Cognito、SES、S3、CloudFront、SQS、SSM）とNeonで、費用の見込みは月約4.50円だった。大関の判断の前提は次のとおり。

- 売上は0円のプロダクトなので、インフラの費用は多少かけてよい。
- 個人開発で世には出さない。そこまで高い品質は求めない。
- アーキテクチャの設計からやり直してよい。

実装はもう始まっていた。`main`にはAWSの初回準備（Terraformの状態バケット、GitHub ActionsのOIDC、SSMの登録スクリプト）とCIが入り、AWSの環境（PR #91）とPostgres向けのDB変更の仕組み（PR #92）が開いていた。

## 決定

### 1. 画面・API・DB・画像・リマインド・ログインを、すべてCloudflareに置く

AWSとNeonは使わない。部品は次のように置き換える。

| いままで | これから |
| --- | --- |
| API Gateway＋Lambda `api` | Workers（VoidのAPIの置き場所`routes/`） |
| CloudFront＋S3（画面） | Workersの静的ファイル（VoidのSPA＋APIの形） |
| Neon（Postgres） | D1（SQLite） |
| S3（グッズの画像） | R2。署名付きURL、取得の期限5分、`uploads/`に置いて確定のときにコピー、確定しなかったものはライフサイクルで1日後に消す、をそのまま移す。ロックが無いので、確定と解散・退会は決定6の下の手順で重ならないようにする |
| EventBridge Schedulerと`notification-sender` | 1分ごとのCron（決定4） |
| Lambda `erasure-worker` | Queuesの受け手。止まったジョブは1分ごとのCronが拾い直す。Queuesの再試行を使い切って失敗キューに移ったジョブは、D1のジョブの行を「失敗」にし、Cronは拾い直さない（オーナーが見て判断する） |
| SQSの失敗キュー | Queuesの失敗キュー（dead letter queue） |
| Cognito＋SES | Better Authのパスキー。メールは送らない（決定5） |
| SSM Parameter Store | Workersのsecret（`void secret put`） |
| CloudWatch Logs | Workersのログ。保存は無料プランの日数（AWS構成のC-3の7日より短い） |

D1はアジアに寄せて置く（location hint）。結合検証と本番は、Workers・D1・R2を2組作って分ける（最初の1本の要件F-01）。Voidでの分け方は、最初の1本の設計書を直すときに確かめる。（2026-11-28の追記：Voidは自分のアカウントへの配置で配置先を1つしか持てないので、結合検証は作らず本番だけにした。最初の1本の論点fs-env）

### 2. 費用は0円にし、Workersの無料プランで動かす

最初は、費用をかけてもよいとしてWorkers Paid（月5ドル）を選んだ。2026-11-27に大関が「あくまで個人開発で、5ドルもかけたくない」と言い直したので、無料プランにする。無料プランの上限は次のとおり（2026-11-27にCloudflareの資料で確かめた）。

| 部品 | 無料プランの上限 | yoinの使い方 |
| --- | --- | --- |
| Workers | 1日10万リクエスト、1回の処理のCPU時間10ミリ秒（Cronも同じ）、Cronは1アカウント5個 | 10人で使い、Cronは1個 |
| D1 | 1日に読み取り500万行、書き込み10万行。保存は合わせて5GB | 毎分のCronは索引で数行だけ読む |
| R2 | 保存10GB、書き込みの操作月100万回、読み取りの操作月1,000万回 | グッズの画像だけ |
| Queues | 1日1万操作、メッセージの保持は24時間（2026-02-04から無料プランで使える） | 解散・退会・外すのジョブだけ |

Workers・D1・Queuesは、上限を超えても料金はかからず、その日の処理がエラーで止まる。R2は違い、無料の枠を超えた保存と操作には従量の料金がかかる（https://developers.cloudflare.com/r2/pricing/ ）。そこで、R2が無料の枠を超えないように、APIで画像1枚の大きさとグループごとの枚数に上限を付ける。10GBは300KBの画像で約3万枚なので、10人の使い方なら大きく余る。上限の値は、データモデルを直すときに決める。R2を使うにはCloudflareに支払い方法の登録が要る見込みだが、確かめていない（推測）。ログインはメールを送らない形にした（決定5）。無料プランのEmail Serviceは登録済みの宛先にしか送れず、送るにはCloudflareに置いたドメインも要るためである。

CPU時間の10ミリ秒に、Web Pushの暗号化とパスキーの確かめが収まるかは確かめていない。最初の1本の実装の前に、大関の手元で一度だけ計る。収まらなければ、1回のCronで送る件数を減らすか、有料プランに替えるかを大関が決める。

### 3. バックエンドはVoidで組み、配置は`void deploy`にする

Void（VoidZeroが作り、2026-10-15にMITライセンスで公開。2026-11-27時点のnpmの版は1.12.2）を使う。VoidはViteの上に作ったCloudflare向けのフレームワークと配置の道具で、中でHonoを使う。

- APIは`routes/`に置き、Honoの書き方（Honoのcontext）で書く。入力の検査はZodのまま。
- 画面はいまのReact＋Viteを「SPA＋API」の形で載せる。PWAとService Workerはそのまま。
- DBはD1とDrizzle（Voidに入っている`void/db`）。マイグレーションは`void db generate`で作り、`void deploy`のときに流す。手でSQLを流す手順は作らない。
- 画面からAPIを呼ぶ型つきのクライアントは、`hono/client`からVoidの`void/client`に替える。
- 配置は`void deploy`にする。資源（D1、R2、Queues、Cron）の作成、マイグレーション、配置を1回で行い、中でCloudflareのcf CLIを使う。CIは`CLOUDFLARE_API_TOKEN`で動かし、トークンはGitHubのSecretsに置く。
- 文脈ごとの層（ADR-0003）は`src/contexts/`に置いたまま、`routes/`・`crons/`などVoidの置き場所からは文脈の公開関数だけを呼ぶ。境目はeslint-plugin-boundariesで今どおり検査する。
- Devinには、Voidに付いているエージェント向けの文書（`AGENTS_TEMPLATE.md`とスキル）を読ませる。

### 4. リマインドは、1分ごとのCronでD1を見て送る

リマインド1件ごとの予約は作らない。リマインドの行に送信時刻を持ち、1分ごとのCronが送信時刻の来た行を引き受けて、Web Pushで送る。取り消しは行を書き換えるだけになる。

送信の決まりはデータモデルのまま守る。同じ行を2回見ても、引き受けに成功した実行だけが送る。`sending`のまま止まった行は10分後に引き受け直す。送り直しは、送れていない端末だけにする。送信期限（最初の1本の設計どおり、送信時刻の1時間後）を過ぎた行は送らず、送れなかったものとして残す。

D1を過去の時点に戻したときは、実際には届いた通知もDBでは未送信に戻る。そこで、戻す前にCronを止め、その止めた時刻を記録する。戻したあと、送信時刻がCronを止めた時刻より前の行を送らないものに変えてから、Cronを再開する。境目を戻した先の時刻にすると、戻した先からCronを止めるまでに送った通知をもう一度送ってしまうためである。この手順は、最初の1本の設計書を直すときに書く。

D1は使わないあいだも眠らないので、毎分見ても費用は増えない。送信は最大1分遅れる。

Web Pushの暗号は、Web Cryptoで書いたライブラリ（pushforgeなど）で行う。iPhoneへ届くかは結合検証で確かめる。

### 5. ログインはVoidのBetter Authで、パスキーにする

Voidに入っているBetter Authに、パスキーでログインする機能を足す。パスキーは、端末の顔認証や指紋で本人を確かめ、端末に置いた鍵でログインする方法である。メールのコードはやめ、メールは送らない（2026-11-27、大関の判断）。2026-11-21に「パスキーは使わない」と決めた判断は、これで置き換える。メールを送るにはドメインと送信のサービスが要り、無料のままでは組めないためである。

- 招待リンクを開いた人は、その場でパスキーを登録してユーザーになる。招待リンクを通らないログインだけでユーザーを作らない決まりは変えない。Better Authがユーザーを作る前に呼ぶつなぎ目で、有効な招待のトークンを確かめ、無ければ断る。
- iPhoneのパスキーはiCloudキーチェーンで同じApple IDの端末に移る。端末をすべてなくした人は、オーナーが招待を出し直し、本人がパスキーを登録し直す。前のアカウントに戻す手順は、最初の1本の設計書を直すときに決める。
- メールアドレスを持たなくなるので、個人の情報はAWSのときより減る。
- パスキーは登録したときのドメインに結び付く。あとで配信のドメイン（`workers.dev`の名前や独自ドメイン）を替えると、登録済みのパスキーがすべて使えなくなる。使うドメインは、最初の1本の設計書で最初に固定する。

ログインの状態はD1の表に置く。グループの操作は、読み取りも書き込みもメンバーであることを確かめてから行う。

### 6. D1の書き込みは、先に読んでから、条件を付けた`batch()`でまとめて流す

D1はWorkersから`BEGIN`・`COMMIT`のトランザクションを書けないので、ADR-0002の決定3（最初にグループの行を`FOR SHARE`でロックし、1つのトランザクションで書く）は次の形に置き換える。

1. グループと対象の行を読み、書いてよいかを判断する。
2. 書き込みは`db.batch()`でまとめて流す。どの文にも、同じ条件（「グループが有効」「申込がまだ前の状態」など）を`WHERE`で付ける。
3. 前の文の結果で条件が変わってしまい、同じ条件を付けられない書き込みは、条件が外れたら失敗する確かめの文を`batch()`の先頭に置く。確かめの文は、条件が外れたときに制約（`CHECK`など）に反する行を書く形にする。
4. 流したあと、各文が変えた件数を見て、条件が外れていたら利用者に、もう一度試すよう出す。

D1の`batch()`は、どれかの文が失敗（エラー）すると全部を取り消す。条件が外れて0件しか変えなかった文は失敗ではないので、それだけでは取り消されない。そこで、手順2ではすべての文に同じ条件を付けて、条件が外れればどの文も何も変えないようにする。手順3では、確かめの文をわざと失敗させて全部を取り消す。D1は1つのDBで1度に1つの処理しかしないので、`batch()`の途中にほかの書き込み（解散など）は割り込まない。書き込みごとの条件と、どれに確かめの文を使うかは、データモデルを直すときに表ごとに書く。

R2の画像はD1の`batch()`に入らないので、画像の確定と解散・退会は、ロックの代わりに次の手順で重ならないようにする。

1. 画像を確定するAPIは、R2でコピーする前に、D1へ「確定中」の記録を書く。書くのは、グループと操作した人の所属が有効という条件を付けた`batch()`である。
2. コピーが終わったら、品目の行を書き、確定中の記録を消す。これも同じ条件を付けた`batch()`にする。この`batch()`が条件で外れたら（グループか所属がもう有効でない）、APIはコピーした画像を自分で消す。
3. 解散・退会・外すは、先にグループや所属の状態を変え、新しい確定中の記録を書けなくする。そのあと、D1の品目の行と確定中の記録にあるキーの画像を消す。さらに、R2で置き場を一覧して、残っている画像を消す。一覧して消す範囲は、解散ならグループの置き場（`groups/<group_id>/`）の下すべて、退会と外すなら、そのとき抜けた所属の下書きの置き場（`groups/<group_id>/drafts/<user_id>/<joined_at>/`）の下だけにする。下書きのキーに入った時刻（`members.joined_at`）を入れるのは、入り直すと入った時刻が変わって置き場が分かれ、前の所属の片づけ（12時間後のやり直しを含む）が入り直したあとの画像を消さないようにするためである。確定した品目の画像（`items/`の下）は、作った人が退会や脱退をしても残す（データモデルの決まりのまま）。
4. 片づけのジョブは、終わるときに、手順3と同じ範囲の一覧と削除を12時間後にもう一度流すメッセージを、Queuesの遅延で入れる。

HTTPで動くWorkerには実行時間の上限が無い（Cloudflareの仕様）。そのため、待てばコピーが届かなくなる、という時間の前提は置かない。手順2で、状態を変えたあとに終わったコピーはAPIが消す。APIがコピーのあと止まって残った画像は、手順4のやり直しで消す。退会した人の確定が`items/`の下に残した画像は、どの品目も指さないまま、グループの解散のときに消える。手順4より後にコピーが届くと残るが、1回のコピーが12時間を超えることは考えない。12時間にするのは、無料プランのQueuesがメッセージを24時間しか持たないため、遅らせたメッセージが消えないように余裕をとるためである。記録の表と、画像のキーの付け方は、データモデルを直すときに決める。

## 選ばなかった案

詳しくは[論点の記録](../discussions/cloudflare-migration.md)にある。

- DBはNeonのまま、Hyperdriveでつなぐ。ADR-0002の書き込みの決まりをそのまま使えるが、管理するものがCloudflareとNeonの2つ残る。大関はCloudflareにまとめるほうを選んだ。
- 画面とAPIだけCloudflareに移し、認証とリマインドはAWSに残す。管理するものがAWS・Cloudflare・Neonの3つに増える。
- 移さない。費用は月約4.50円のままだが、Cloudflareにまとめない。
- Workers Paid（月5ドル）で動かし、ログインはメールのコードにする。一度は選んだが、大関が費用をかけないほうを選んだ。
- 無料プランで、ログインのメールをResendなど外のサービスから送る。送信元のドメインが要り、年に1,500円ほどかかる見込み（推測）。
- ログインにCognitoだけ残す。AWSのアカウントとSESの管理が残る。ClerkやAuth0などの外のサービスは、管理画面がもう1つ増える。
- リマインドを1件ごとのDurable Objectのアラームや、Workflowsで起動する。いまの予約の形に近いが、DBがD1なら毎分見るほうが作りが単純になる。
- バックエンドをHono単体で組む。ADR-0004の形のままだが、ログイン・マイグレーション・Cron・配置のつなぎ込みを自分たちで作る。
- 配置をcf CLI（1.0.0-rc.6）かwranglerで書く。Voidを使うので、Voidに任せる。
- グループごとにDurable Objectを置いて書き込みを1本にする。通り道とDBが2つに分かれる。条件を付けずに取りこぼしを許す案は、解散したグループに行が残り、データの消失の決まりに当たる。

## 結果

### 良くなること

- 管理するのがCloudflareのアカウント1つになる。AWSのアカウント、Terraformの状態バケット、SSM、Neonが要らなくなる。
- DBを過去の時点に戻せる期間が、Neonの無料プランの6時間から、D1の無料プランの7日に延びる。
- 費用は0円のままで、AWSのときの月約4.50円より下がる。
- 土台（マイグレーション、ログイン、資源の作成、配置）をVoidが持つので、Devinに渡す土台のタスクが減る。
- リマインドの予約を作る・消す・世代を切り替える処理が要らなくなる。
- 手元でD1・R2・Cronをまねて動かせるので、AWS Emulator（ADR-0004の2026-11-25の追記）は要らなくなる。

### 悪くなること・残るリスク

- 無料プランの上限を超えると、その日の処理が止まる。とくに1回のCPU時間10ミリ秒に、Web Pushとパスキーの確かめが収まるかは確かめていない。
- ログのWorkersでの保存が、AWSのときの7日より短くなる。
- パスキーを持つ端末をすべてなくすと、招待し直すまでログインできない。
- Voidは公開から6週間で、利用の記録が少ない。確かめたのはnpmのパッケージの文書だけで、実際には動かしていない。
- D1は途中で判断を挟むトランザクションが無いので、書き込みの条件を付け忘れると決まりが崩れる。データモデルを直すときに条件を表ごとに書き、試験で確かめる。
- CIからの配置は、期限の長いAPIトークンになる。GitHubのOIDCで短い認証にできるかは確かめていない。トークンの権限は配置に要るものだけにする。
- マージ済みのAWSの初回準備（`infra/terraform/bootstrap/`、`scripts/bootstrap-ssm.ts`）と、CIの成果物の作り（Lambdaの束ね方）は作り直しになる。

## この決定では決めないこと

- 無料プランの上限に近づいたことの見張り方（ADR-0006の決定5のAWS Budgetsの代わり）。
- 流量の上限と、要求が急に増えたときの知らせ方（ADR-0006の決定6・決定7の代わり）。
- 失敗キューに入ったときの知らせ方（AWS構成のC-4の代わり）。
- 結合検証と本番を、Voidでどう分けるか。（2026-11-28：本番だけにした。最初の1本の論点fs-env）
- 端末をすべてなくした人を、前のアカウントに戻す手順。（2026-11-28：オーナーが出す戻すリンクにした。最初の1本の論点fs-recover）
