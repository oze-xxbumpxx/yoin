- 関連：[文脈マップ](context-map.md)、[用語集](glossary.md)、[ADR-0001](decisions/ADR-0001-bounded-contexts.md)、[PR/FAQ](prfaq.md)
- データベース：CloudflareのD1（SQLite）の1つのデータベース。SQLiteにはスキーマが無いので、表の名前の頭に文脈の名前を付けて分ける（R19）

## 全体の決まり

- IDはUUIDv7をアプリで作る。
- テーブル名は用語集の英語名を複数形のスネークケースにする（`TicketApplication` → `ticket_applications`）。列もスネークケース。
- 文脈の名前はモジュール名と同じ。`group`だけはSQLの予約語なので`groups`にする。この文書の見出しの`groups.users`は、D1では`groups_users`という名前の表になる（文脈の名前、`_`、表の名前。R19）。
- 状態は`text`とCHECK制約で持つ。値は英語の小文字。
- 公演の日と開場・開演時刻は日本時間の`date`と`time`。チケットの期限とリマインドの送信時刻は`timestamptz`。
- 下の表の型は、D1では次の形で持つ（R19）。SQLiteの型は少ないので、形はCHECK制約とアプリの入力の検査で守る。

| この文書の型 | D1での持ち方 |
|---|---|
| `uuid` | `text`。UUIDv7の文字列 |
| `timestamptz` | `integer`。UTCのミリ秒。大小をそのまま比べられ、索引も効く |
| `date`・`time` | `text`。日本時間の`YYYY-MM-DD`と`HH:MM` |
| `smallint`・`int`・`bigint` | `integer` |
| `jsonb`・`text[]` | `text`。JSONの文字列。中身はアプリがZodで確かめる |

- 部分一意インデックス（`WHERE`付きの一意）はSQLiteでも使える。Postgresの`NULLS NOT DISTINCT`は無いので、nullになる列は`ifnull(列, '')`の式で一意にする。
- 外部キーはD1で既定で効く。複合外部キーも使える。
- 合計金額、受取できるか、行ったかどうかは保存せず、その場で計算する。
- ほかの文脈がメンバーを指すときは、`user_id`と`group_id`で持つ。
- 特に書いていない列はnull不可。

## 外部キーと、消したときの動き

外部キーごとに、親に従って消えるか、使われていれば消せないかを決める（YADR-07）。

| 動き | 外部キー |
|---|---|
| CASCADE（親に従って消える） | members・invite_links → groups、setlists・concert_artists → concerts、setlist_items → setlists、attendance_records・concert_snapshots → attendances、companions → attendance_records、distributions → ticket_applications、buyers・merch_requests → merch_listsとmerch_items、reminder_deliveries → remindersとpush_subscriptions |
| RESTRICT（使われていれば消せない） | concerts.venue_id、concerts.tour_id、concert_artists.artist_id、groups.owner_user_id、members.user_id（退会ではmembersを消してからusersを消す） |
| SET NULL | setlist_items.artist_id |

- 同じスキーマの中で別の行を指すときは、`(group_id, venue_id)`のように所属を含む複合外部キーにする。参照される側に`(group_id, id)`の一意制約を付ける。別グループの会場や品目は結べない。
- 文脈をまたぐID（公演ID、ツアーID、グループID、ユーザーID）には、RESTRICTの外部キーだけを張る。CASCADEは使わない。消す順番はコードが決め、順番を間違えたときにDBが断る。
- このため、マイグレーションはgroups → catalog → attendance・ticket・merch・notificationの順に流す。

## グループの所属と権限（YADR-01）

- 操作した人のIDは、リクエストの中身ではなくログインのセッションから取る（2026-11-27、ADR-0008の決定5。もとはJWT）。
- 各文脈の公開関数は「操作した人」と「グループID」を受け取り、対象の行と、指定されたID（公演、会場、品目、メンバーなど）がすべて同じグループのものかを確かめる。違えば、存在しないときと同じ「見つからない」を返し、参照先の中身も返さない。
- グッズリストに載せる品目は、そのリストの公演か、公演のツアーのものに限る。

| 操作 | できる人 |
|---|---|
| アーティスト、ツアー、公演、会場、セトリ、品目の登録・編集 | グループのメンバー全員 |
| チケット申込の編集・削除、分配先の指定 | 申込者だけ |
| 購入担当の指定 | グループのメンバー全員。担当にできるのは同じグループのメンバー |
| 頼まれ物の編集・削除 | 頼んだ本人だけ |
| 買えた・売り切れの印を付ける・外す | その品目の購入担当だけ（R14） |
| 参戦と参戦記録（座席、同行者、ひとこと）を見る | グループのメンバー全員。解散や外されたあとに本人に残った参戦は本人だけ（R8） |
| 参戦と参戦記録の編集・削除 | 本人だけ |
| 招待リンクの発行、解散 | オーナーだけ（自分用グループではできない） |
| メンバーを外す | オーナーだけ。自分自身は外せない（R10） |
| グループを抜ける | メンバー本人。オーナーは一番前から参加しているメンバーに引き継いでから抜ける。ほかにメンバーがいなければ解散を案内する。自分用グループは抜けられない（R10） |

## 書き込みの順番（YADR-02、R20）

D1はWorkersから`BEGIN`・`COMMIT`のトランザクションを書けず、`FOR SHARE`のロックも無い（ADR-0008の決定6）。そこで、書き込みは次の形にする。

1. 先に読んで、書いてよいかを判断する。グループ（`groups.status = active`）、操作した人（`users.status = active`、`members.status = active`）、対象の行の状態や版番号を読む。
2. 書き込みは全部を1つの`db.batch()`にまとめる。D1は1つのDBで1度に1つの処理しかしないので、`batch()`の途中にほかの書き込み（解散など）は割り込まない。
3. `batch()`の先頭に、確かめの文を置く。確かめの文は、手順1で確かめた条件がまだ成り立つかを見て、成り立たなければ`CHECK`に反する行を書いて失敗する。失敗すると`batch()`の全部が取り消される。
4. `batch()`の途中の文で条件が変わる書き込み（前の文が消した行の数で次の文の値が決まるなど）は、その文の直前にもう1つ確かめの文を置く。
5. 確かめの文で失敗したら、利用者にもう一度試すよう出す。

確かめの文は、どの行も持たない表`write_guards`（列は`ok integer NOT NULL CHECK (ok = 1)`だけ）に、`INSERT INTO write_guards (ok) SELECT 0 WHERE NOT EXISTS (条件を満たす行)`の形で書く。条件が成り立てば何も書かず、成り立たなければ0を書こうとして`CHECK`で失敗する。

| 書き込み | 先頭の確かめの文で見る条件 | 途中の確かめの文 |
|---|---|---|
| グループの中の書き込み全部（公演、セトリ、参戦、申込、グッズなど） | グループが`active`、操作した人が`active`、その人の所属が`active` | なし |
| 同行者・分配先・購入担当に別のメンバーを指定する | 上に加えて、指定されたユーザーと所属が`active` | なし |
| セトリの保存 | 上に加えて、`setlists.version`が読んだ版のまま | なし |
| 申込の状態を変える、期限を直す、申込を消す | 上に加えて、申込の`updated_at`が読んだ値のまま。`updated_at`は書くたびに`max(今の時刻, 前の値 + 1)`にするので、同じミリ秒の2回の書き込みでも値が変わる。状態だけでなく期限の変更も見るので、古い読み取りで通知の差分を計算した書き込みは断られる | なし |
| 招待リンクから登録する（R24） | 招待リンクが期限内、取り消されていない、`used_count < max_uses`。確かめの文で断られたら、APIはその要求で作ったBetter Authのユーザーとパスキーを消す | なし |
| 公演の下書きを確定する | 上の1行目に加えて、下書きがまだある | なし |
| 解散・退会・外すの段（同行者を消して人数に足すなど） | ジョブの行が読んだ`step`のまま | 同行者を消す文のあと、人数に足す文の前に、消した行の数が読んだ数と同じか |

- 解散、退会、メンバーを外す・抜けるの開始は、その行を`disbanding` / `withdrawing` / `leaving`に変える`batch()`である。それより前に流れた書き込みは、解散などの片づけの対象に入る。それよりあとの書き込みは、先頭の確かめの文で断られる。
- ほかの文脈の表を読むことにはならない。グループの公開関数が、確かめの文を`batch()`に足すだけ。

## グループは1人でもよい

- 1人で行く公演も記録できるように、メンバーが1人だけのグループを認める。`groups.kind`で、仲間と使うグループ（`shared`）と自分用グループ（`personal`）を分ける。
- ユーザー登録のときに、自分用グループを1つだけ自動で作る。招待リンクは出せず、解散もできない。グループ一覧では「自分用」として分けて見せる。
- メンバーなら誰でも、仲間と使うグループを新しく作れる。新しい人の登録には、今までどおり招待リンクが要る。

## アーティストごとのまとめ方

- アーティストはグループごとに登録する。公演とアーティストは`catalog.concert_artists`で多対多にし、フェスと対バンを1件の公演で表す。
- `artists.name_key`に名前を正規化した値（NFKC、小文字、空白を除く）を持ち、グループの中で一意にする。
- 本人の参戦をアーティストごとにまとめるときは、グループをまたいで`name_key`でまとめる。解散後の参戦は`concert_snapshots.artist_name_keys`を使う。
- セトリの曲目に`artist_id`を持たせ、フェスでどのアーティストの曲かを示す。
- ツアーにはアーティストを持たせず、ツアーの公演に付いたアーティストから表示する。

名前でまとめるので、次の誤差が出る。MVP1ではこれを受け入れる（2026-11-07、YADR-09）。まとめ直す機能はMVP2で曲マスタと一緒に考える。

| 場合 | 例 | 集計 |
|---|---|---|
| 改名 | 「ネオン・パレード」が「NEON PARADE」に改名し、グループで名前を直した。改名前に解散したグループの写しは旧名のまま | 旧名と新名が別の行に出る |
| 同じ名前の別のアーティスト | 2つのグループに、別人の「ミナト」がいる | 1つの行に合算される |
| 表記ゆれ | 「ネオン・パレード」と「ネオンパレード」 | 正規化で「・」は消えないので別の行に出る。グループの中では、登録済みのアーティストを選ぶ画面で防ぐ |

## 解散と退会

### 動かし方（YADR-03、Q5、R23）

- APIは解散・退会・メンバーを外す（抜ける）を受け付けると、1つの`batch()`で状態を`disbanding` / `withdrawing` / `leaving`にし、`groups.erasure_jobs`に行を作る。そのあとQueuesにジョブを入れて、すぐ応答する。
- 処理はQueuesの受け手が行う。誰も画面を開かなくても最後まで進む。
- 1分ごとのCron（リマインドと同じもの）が、`running`のまま`queued_at`と`updated_at`が15分より前のジョブを見つけて、Queuesに入れ直す。Queuesへ入れる前にAPIが止まったジョブも、これで拾う。15分は、Queuesの受け手の1回の実行の上限である。受け手は段を進めるたびに`updated_at`を更新する。
- Queuesの再試行を使い切ったジョブは失敗キューに移る。失敗キューの受け手は、ジョブの行を`failed`にする。Cronは`failed`を入れ直さない。知らせ方はADR-0008の「決めないこと」に回した。
- 段階ごとに`erasure_jobs.step`を進める。DBだけで済む処理は1つの`batch()`にまとめる（申込の削除と通知の予約の取り消し、同行者の削除と人数の加算、写しの作成と`concert_id`のnull化）。同行者の削除と人数の加算は、途中の確かめの文を使う（上の「書き込みの順番」）。
- R2の画像は、品目や下書きを消すのと同じ`batch()`で`merch.object_deletions`にキーを書く。R2から消せたキーだけ行を消し、失敗したキーは次の回にやり直す。
- どの段階も「まだ残っている行だけを処理する」形にし、2回動いても結果が変わらないようにする。
- 無料プランでは、Queuesの受け手も1回の処理のCPU時間が10ミリ秒までになる見込みである（ADR-0008の決定2）。1回に処理する行の数を少なくし、残りは同じジョブをQueuesに入れ直して続ける。

### 画像の確定と、解散・退会・外す（R13、R21）

画像のアップロードは、一時置き場（`uploads/<group_id>/<user_id>/`の下）を通す（R13）。APIは確定のとき、キーのグループと本人が操作した人に合うかを確かめる（2026-11-21）。端末は一時置き場に上げてから、APIに確定を頼む。`groups/`の下に直接上げるURLは出さない。一時置き場はR2のライフサイクルの設定で1日後に消えるので、確定されなかった画像も残らない。

コピー先のキーは、確定した品目なら`groups/<group_id>/items/`、下書きなら`groups/<group_id>/drafts/<user_id>/<joined_at>/`の下にする。`<joined_at>`は、そのときの所属の`members.joined_at`（UTCのミリ秒）である。抜けて入り直すと`joined_at`が変わるので、前の所属の片づけが、入り直したあとの下書きの画像を消さない。

ロックが無いので、確定は次の順で行う（ADR-0008の決定6）。

1. `batch()`で`merch.image_confirmations`に確定中の記録を書く。記録には、そのときの所属の`joined_at`も書く。先頭の確かめの文で、グループと操作した人の所属が`active`か、コピー先のキーが`object_deletions`に無いか、R2の枚数が上限より少ないか（下の「R2の費用を0円に保つ上限」）を見る。コピー先のキーは下書きIDと一時置き場のキーから決まるので、やり直しは同じキーになる。削除待ちのキーを断るのは、前の片づけがR2から消す前に同じキーで確定し直すと、確定した画像があとから消えるためである。削除待ちで断ったら、利用者にしばらくしてから試すよう出す。R2から消せたら`object_deletions`の行が消え、同じキーで確定できるようになる。
2. R2の中でコピーする。
3. `batch()`で品目や下書きの`image_key`を書き、確定中の記録を消す。先頭の確かめの文は、1と同じ条件に加えて、所属の`joined_at`が確定中の記録の`joined_at`と同じかを見る。コピーの途中で抜けて入り直した人の確定は、ここで失敗する。コピー先の下書きの置き場は前の所属のものなので、通すと前の所属の片づけで消えてしまうためである。この`batch()`が確かめの文で失敗したら、APIは後始末をする。コピー先のキーは同じ画像のやり直しで同じになるので、無条件には消さない。後始末は、Cronの片づけと同じく、まず`batch()`でキーを`object_deletions`に書き、それからR2の画像を消す。この`batch()`の先頭の確かめの文は、そのキーの確定中の記録が自分の書いたもの（`started_at`が同じ）のままか無いこと、ほかの確定中の記録が無いこと、品目と下書きのどれもそのキーを指していないことを見る。別の要求が同じキーで確定し直していれば、確かめの文で失敗し、APIは何も消さない。`object_deletions`に書いたあとは、手順1がそのキーを断るので、消しているあいだに確定し直されることもない。
4. 下書きを品目に確定するときは、画像を`drafts/`の下から`items/`の下にコピーし、品目の`image_key`には`items/`のキーを書いて、下書きのキーは`object_deletions`に入れる。こうすると、確定した品目の画像は作った人の退会や脱退で消えない。

確定は、同じ画像で何度やり直しても結果が変わらない。手順3の確かめの文は、確定中の記録がまだあることも見る。

APIが手順1と3のあいだで止まると、確定中の記録が残る。1分ごとのCronは、`started_at`が15分より前の記録を片づける。片づけは、記録を消してキーを`object_deletions`に書く`batch()`（先頭の確かめの文で、記録がまだあるかを見る）のあとに、R2からその画像を消す。APIの手順3とCronの片づけは、どちらも確定中の記録があることを確かめるので、通るのは片方だけである。APIがまだ動いていて手順3が先に通れば、Cronは何もしない。Cronが先なら、APIの手順3は失敗し、利用者にもう一度試すよう出す。

解散・退会・外すの片づけでは、次の順で画像を消す。

1. 状態を変えた`batch()`より後は、新しい確定中の記録を書けない。
2. `object_deletions`と`image_confirmations`にあるキーの画像を消す。
3. R2で置き場を一覧して、残っている画像を消す。解散なら`groups/<group_id>/`の下すべて、退会と外すなら`erasure_jobs.drafts_prefixes`の置き場の下だけにする。
4. 最後の段で、手順3と同じ範囲を12時間後にもう一度一覧して消す予定を`merch.prefix_sweeps`に書く。1分ごとのCronが時刻の来た行をQueuesに入れ、消し終えたら行を消す。APIがコピーのあと止まって残った画像は、これで消える。

APIがコピーのあと止まって`items/`の下に残った画像は、どの品目も指さないまま、グループの解散のときに消える。

### R2の費用を0円に保つ上限（R25）

0円は運用の目標ではなく、上限として守る（2026-11-27 オーナーの決定）。R2は無料の枠を超えると従量の料金がかかるので、枠に近づいたら新しい画像を受け付けない。

- 枚数の上限は、全部のグループを合わせて4,000枚。1枚2MBまでなので、最大でも8GBで無料の10GBに収まる。
- 数えるのは、R2に置かれるオブジェクトの数である。品目と下書きが指す画像、`upload_grants`のうち期限の来ていない分（一時置き場。確定したあとも1日残るので、確定しても数から外さない）、`image_confirmations`（確定中のコピー先）、`object_deletions`（削除待ち）を足す。
- この数は、増やす書き込みの`batch()`の先頭の確かめの文で、上限より少ないかを見る。増やす書き込みは2つある。一時置き場へのURLを出すとき（`upload_grants`に行を書く）と、確定の手順1（`image_confirmations`に行を書き、コピー先の分を取る）である。1枚の画像は一時置き場とコピー先の2つを数えるので、URLだけを先にたくさん取っても、確定のときのコピーで上限を超えない。
- R2の操作の回数は、`r2_usage`に月ごとに数える。class A（書き込み・一覧・コピー）は無料の枠が月100万回、class B（読み取り）は月1,000万回である。どちらかが枠の8割に達したら、その月は新しい画像のURLを出さない。取得のURLを出すのも8割で止め、画面は画像の代わりに「今月は画像を表示できません」と出す。
- 上限で断ったときも、下書きと品目は画像なしで保存できる。画像はあとから付け直せる。

### 解散で残すもの（Q2）

- 公演日が解散した日（日本時間）以前の参戦は、本人に残す。参戦ごとに`concert_snapshots`を作り、`concert_id`と`group_id`をnullにする。参戦記録がなくても残す。
- 公演日が解散した日より後の参戦（これからの予定）は消す。
- 解散後の参戦は、本人だけが読める。

### 退会で消す範囲（Q1）

- 消すもの：本人だけのデータ。アカウント（Better Authのユーザー・セッション・パスキーと`users`）、本人あての戻すリンク、メンバーの行、参戦と参戦記録と写し、本人が申込者の申込、頼まれ物、下書き、通知の予約と端末。
- 残すもの：グループの全員のデータ。公演、セトリ、確定した品目と画像は残し、作った人の情報は持たない（`setlists.updated_by`はnullにする）。
- ほかの人のデータの中の本人：同行者は人数に置き換える。分配先は空に戻す。購入担当は担当なしに戻す。
- ログには個人の情報を書かない。D1を過去の時点に戻せる期間（無料プランで7日。ADR-0008）のあいだは、消したデータを戻せる。このことを外部FAQに書く。
- メールは送らないので、メールの送信の抑止リストは無い（もとはSESの抑止リストを消す対象にしていた）。
- 画像のR2のバケットは古い版を残さない。消した画像が完全に消えるようにする（2026-11-21、R18）。

### 退会の手順（YADR-04）

1. `users.status`を`withdrawing`にする（`batch()`。先頭の確かめの文で`active`を見る）。画面には「退会を受け付けました」と出す。
2. 同じ`batch()`で、Better Authの本人のセッションを消す。パスキーは残っていても、`users.status`の確認で断れる。
3. Queuesの受け手がアプリのデータを消す。本人のセッションは要らない。
4. Better Authの本人のユーザーとパスキーを消す。
5. `users`の行を消す。最後の段で、同じ`batch()`で`merch.prefix_sweeps`に12時間後の片づけを書いてから`erasure_jobs`の行を消す（R17、R21）。

- 仲間と使うグループのオーナーなら、1の前に一番前から参加しているメンバーへ引き継ぐ。ほかにメンバーがいなければ、そのグループを解散する。自分用グループは解散と同じ順で消す。
- APIはセッションが有効かに加えて、`users`の行が`active`かを毎回確かめる。
- `users`の行は、招待リンクから登録したときと、最初のオーナーを作るときだけ作る。Better Authのユーザーがいても、`users`の行が無ければ何もできない。
- 招待リンクの回数や期限で登録を断ったとき、APIはその要求で作ったBetter Authのユーザーとパスキーを消す。消す前にAPIが止まって残ったもの（`users`の行から指されないBetter Authのユーザーで、作ってから1時間より前のもの）は、1分ごとのCronが消す（R24）。

### メンバーを外す・自分から抜ける（R10）

- 外すのも抜けるのも同じ処理（`erasure_jobs.kind = leave`）で、その人の、そのグループでのデータだけを扱う。
- 始めに`members.status`を`leaving`にする（`batch()`。先頭の確かめの文で`active`を見る）。その人はそのグループを見られず、書き込みもできなくなる。
- 参戦：公演日が外した（抜けた）日以前の参戦は写しを作って`concert_id`と`group_id`をnullにし、本人に残す。これからの予定は消す。
- チケット：その人が申込者の申込を消し、同じ`batch()`で通知の予約を取り消す。ほかの人の申込でその人に分配した行は、渡し先を空に戻す。
- グッズ：その人の頼まれ物と下書きを消す（下書きの画像はobject_deletionsへ）。購入担当の行を消し、担当なしに戻す。
- ほかのメンバーの参戦記録でその人が同行者になっていたら、名前を人数に置き換える。
- その人あてで、そのグループのオーナーが出した戻すリンクは、始めの`batch()`で`revoked_at`に時刻を入れる。
- 最後にmembersの行を消す。そのあと招待リンクから入り直すことはできる。

## 通知

### 届ける時刻（Q3、YADR-08）

チケットが期限の種類ごとに送信時刻を決め、通知に予約する。

| 期限 | 届ける時刻 | `dedupe_key`の例 |
|---|---|---|
| 結果発表日時 | 発表の時刻 | `ticket:<申込ID>:result` |
| 受取開始日時 | 受取開始の時刻 | `ticket:<申込ID>:pickup` |
| 入金期限 | 前日の20時と、締切の3時間前の2回 | `ticket:<申込ID>:payment:eve`、`ticket:<申込ID>:payment:3h` |

- 予約したときに送信時刻がもう過ぎていた場合は、下の「予約の作り方」の期限判定に従う。

### チケットの状態と予約（R9）

- 当選（`won`）にしたら、入金期限の2回の予約を作る。入金済み（`paid`）にしたら入金期限の予約を取り消し、受取開始の予約を作る。
- 落選、申込の削除、解散、退会、外す・抜けるでは、まだ届いていない予約を取り消す。期限を直したら予約を作り直す。
- 期限切れは保存しない。`won`のまま入金期限を過ぎた申込を「期限切れ」として表示・集計する（受取できるかを計算するのと同じ考え方）。定期の処理が要らず、申込者が期限切れから入金済みに直すのも`won` → `paid`の通常の更新で済む。
- 入金済みにしていない申込には受取開始の予約がないので、期限切れの申込に受取開始の通知は届かない。

### 予約の作り方（R22）

リマインドは、`reminders`の行に送信時刻を書くだけにする。1件ごとの予約は作らない（ADR-0008の決定4。もとはEventBridge Schedulerの1回限りの予約。R11）。1分ごとのCronが送信時刻の来た行を引き受けて送るので、送信は最大1分遅れる。D1は使わないあいだも眠らないので、毎分見ても費用は増えない。

- 予約するとき：`reminders`の行を書く。
- 取り消すとき：`status = 'scheduled'`か`held`の行だけを`canceled`にする。`held`のあいだに申込を直したときも、`held`の行は`scheduled`と同じく取り消し・時刻の変更・履歴への移動の対象にする（2026-11-28）。
- 未送信（`scheduled`）の予約の時刻を直すとき：`status = 'scheduled'`の行だけを条件付きで更新し、`send_at`と`recover_until`を同時に替える。0行なら、もう送り始めているので直さない。
- 状態・期限が変わって旧予約が無効なら、後継の予約がなくても旧行の`dedupe_key`を`history:<旧予約ID>`へ移す。未送信の行は取り消すか、新しい時刻へ切り替える場合は現行キーを保つ。差分の計算時点で`sending`・`sent`・`canceled`なら時刻・送信結果は更新しない。後継が必要なときだけ、元のキーで別IDの行を作る。旧行の送信結果は別IDに引き継がない。
- 予約したときに送信時刻を過ぎていたら、`recover_until`より前なら行を書き、次のCronで送る。`recover_until`ちょうど以降なら書かない。
- その回の送信を終えても一時失敗が残り、5分後が送信期限より前なら、`retry_at`に5分後を入れる（3回まで）。再送回数を使い切るか期限で打ち切ったときは、下の「送り方」の完了処理に進む。

### D1を過去の時点に戻したとき（R22）

戻すと、実際には届いた通知もDBでは未送信に戻る。そこで、送信の記録を、戻しても消えない場所に別に残す（2026-11-27 オーナーの決定）。

- 送信の記録は、本体と別のD1のデータベース（`send_log`）に置く。D1の過去の時点に戻す操作はデータベースごとなので、本体を戻しても`send_log`は戻らない。無料プランでもデータベースは複数作れる。
- 端末に送れたら、本体の`reminder_deliveries`を`sent`にする前に、`send_log`に（予約ID、端末ID、回、送った時刻）を書く。`send_log`に書けなかったら、その端末は本体でも`sent`にしない。送ったのに記録が無いことは起きるが、記録があるのに送っていないことは起きない。
- `send_log`には、送ったときの予約の`send_at`も書く。突き合わせでは、予約の今の`send_at`と同じ記録だけを数える。時刻を直した予約は同じIDのまま`send_at`が変わるためである（2026-11-28）。
- 同じ`yoin-send-log`に、戻すリンクとオーナーの戻しで消したパスキーとセッションの記録（`revocations`）も置き、戻したあと本体に当て直す。戻すと、消したパスキーも本体に戻るためである（2026-11-28）。
- `send_log`は90日より前の行を消す。

戻す手順は次のとおり。手順の細部は最初の1本の設計書に書く。

1. 戻す前にCronを止め、止めた時刻を記録する。
2. 本体を戻したあと、`scheduled`・`sending`の行を`send_log`と突き合わせる。`send_log`に記録がある端末は、本体の`reminder_deliveries`もその回で`sent`にする（一部の端末にしか記録が無い予約も同じ）。対象の端末すべてに送った記録がある予約は、`sent`にして送り直さない。
3. 送った記録が一部にしか無い予約と、`send_at`が戻した先の時点からCronを止めた時刻までにある予約は、`held`（保留）にする。記録で届いたかを確かめられないためである。Cronは`held`を引き受けない。
4. `send_at`が止めた時刻より後の予約は、そのまま残す。
5. Cronを再開する。`held`の予約は、オーナーが1件ずつ確かめて、送るか取り消すかを決める。取り消すときは`canceled`にする。送るときは`recover_until`を今から1時間後にし、`attempts`が0なら`scheduled`に戻す（Cronが初回として引き受け、`attempts`を1にする）。`attempts`が1以上なら`sending`に戻して`claimed_at`と`retry_at`をnullにする（同じ回の続きとして引き受ける）。どちらでも、手順2で`sent`にした端末には送らない。

### 送り方（F5、Q4、R22）

- 1分ごとのCronは、引き受けられる行を`send_at`の早い順に数行だけ選ぶ。引き受けられるのは、DBの現在時刻が`recover_until`より前で、次のどちらかの行である。
  - `scheduled`で、`send_at`が今以前の行。
  - `sending`で、`claimed_at`がnullで、`retry_at`がnullか今以前の行（再送か、上限で止めた回の続き）。
  - `sending`で、`claimed_at`が10分より前の行（途中で止まった回の引き受け直し）。
- 引き受けは、選んだ行を同じ条件で`sending`に更新し、`claimed_at`に今の時刻を入れる条件付きの`UPDATE ... RETURNING`で行う。返ってきた行だけを送る。D1は1度に1つの処理しかしないので、Cronが2回重なっても、同じ行を引き受けられるのは1回だけである。回の数え方は次のとおり。`scheduled`の行（初回）と、`retry_at`が入った行（再送）の引き受けは、`attempts < 4`も条件にして、同じ更新で`attempts`を1増やし、`retry_at`を空にする。`retry_at`がnullで`claimed_at`もnullの行（上限で止めた回の続き）と、`claimed_at`が10分より前の行（引き受け直し）は、同じ回なので`attempts`を増やさない。
- 引き受けたときの`claimed_at`の値を、その回の引き受けの印にする。送信結果の記録、上限で止めて`claimed_at`をnullに戻す更新、再送の`retry_at`を入れる更新、完了処理は、どれも`claimed_at`がその値のままかを条件にする。0行なら、ほかの実行が10分後に引き受け直したので、その実行は何も書かずに止まる。端末ごとのWeb Push要求の直前にも、期限と一緒に`claimed_at`がその値のままかを確かめる。
- 無料プランでは、Cronの1回の処理のCPU時間が10ミリ秒までである（ADR-0008の決定2）。1回のCronで送る端末の数に上限を付ける。上限に達したら、`retry_at`はnullのまま`claimed_at`をnullに戻して止める。次の分のCronがすぐに同じ回の続きとして引き受け、まだ試していない端末に送る。10分待つのは、処理が止まって`claimed_at`が残ったときだけである。上限の値は、大関の手元で計ってから決める。
- 送る端末を選ぶときは、`reminder_deliveries`の`sent`・`gone`を回に関係なく除く。同じ回を再開するときは`attempt_no`がその回と一致する`failed`も除く。結果がまだない端末と、前の回の`failed`だけがその回の対象となる。次の再送回は`attempts`を増やすので、前の回で`failed`だった端末も試せる。
- 端末ごとのWeb Push要求を始める直前も期限を確認する。全対象を試すか、期限ちょうど以降になって残りの送信を止めたあとにだけ、次の再送を判断する。再送回数の上限または期限で次の再送ができなければ完了処理に進む。完了処理は、状態と引き受け時刻を照合する条件付きの更新で行い、他の実行と同時に完了処理をしない。結果が`failed`のままの登録済み端末にだけ`last_failed_at`を保存する。成功時刻・結果・回数は保持し、完了時に`sent`に変更して`retry_at`と`claimed_at`を空にする。送れなかったことの知らせ方は、ADR-0008の「決めないこと」に回した。
- 取り消しは`scheduled`の予約だけを`canceled`にする。引き受けより先に取り消せば送らない。
- 端末ごとの送信結果は、送信のたびに`reminder_deliveries`の同じ行に記録する。結果を記録する前に処理が止まった場合は、同じ回でその端末をもう一度試すことがある。
- 端末に送れたら、その端末の`reminder_deliveries`を`sent`にし、`push_subscriptions.last_failed_at`をnullに戻す。2つの更新は同じ`batch()`で行う。
- 避けるのは取りこぼし。送信の直後に処理が止まったときの重複と、引き受けたあとに取り消された通知が届くことは許す。
- 申込詳細を読むときは、DBの現在時刻が`recover_until`ちょうど以降の`scheduled`・`sending`を表示上だけ`sent`として返す。予約行は更新せず、受理記録は`sent_at`の有無で返す。

## 前の決定から変える点

- 文脈マップとADR-0001では「各文脈はメンバーIDを使う」とした。参戦は解散後も本人に残るので、ユーザーIDとグループIDで持つ形に変える。メンバーかどうかの確認はグループの文脈に聞く点は変えない。2026-11-12にADR-0002の承認で確定した。
- 自分が買う分も`merch_requests`に入れ、頼んだ人と購入担当が違う行を画面で「頼まれ物」として見せる。用語集の定義は変えない。
- 2026-11-06の「文脈をまたぐIDに外部キーを張らない」は、2026-11-07に「RESTRICTだけ張る」に変えた。
- 2026-11-06の「Lambdaは2つ」は、2026-11-07に「`erasure-worker`を足して3つ」に変えた。
- PR/FAQの「通知は期限の当日中に届けばよい」を、期限の種類ごとの時刻に変えた。
- ADR-0008の決定6では、12時間後の置き場の片づけをQueuesの遅延のメッセージにした。受け手が失敗を続けると、24時間でメッセージが消えて片づけも消えるので、予定はD1の`merch.prefix_sweeps`に置き、Cronが時刻の来た行をQueuesに入れる形に変えた（2026-11-27、R21）。
- 2026-11-10、PR #1のレビュー（Codex）を受けて2点を直した。送信の途中で止まったリマインドを10分後に引き受け直せるようにした（見張りの予約を足した）。`erasure_jobs`の一意の決まりを、終わっていない記録だけにかけるようにした。
- 2026-11-27、DBをD1に替えた（ADR-0008）。書き込みのロック（`FOR SHARE`）は確かめの文に、リマインドの1件ごとの予約と見張りは1分ごとのCronに、`erasure-worker`と見張りの予約はQueuesとCronに替えた。`reminders.schedule_name`、`reminder_generation_seq`、`erasure_jobs.watchdog_at`、`invite_links.registration_starts`はやめた。

## 決めないこと

- 工程4以降：インデックスの細部、セトリを同時に編集したときの画面での見せ方
- 1回のCronで送る端末の数と、Queuesの受け手が1回に処理する行の数。無料プランのCPU時間10ミリ秒の中に収まる値を、大関の手元で計ってから決める
- `held`の予約を、オーナーがどの画面かコマンドで確かめるか。最初の1本の設計書で決める
- ADR-0008で決めた：D1、R2、Queuesの無料プランの上限、DBを過去に戻せる期間（無料プランで7日）
- MVP2：曲マスタとアーティストのまとめ直し、下書きの`payload`に自動入力の出所を足すか
