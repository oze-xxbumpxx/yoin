# レビュー

もとはリポジトリ直下の`AGENTS.md`の「レビュー」。中身は移しただけで、決まりは変えていない。毎回のレビュー基準（`## Code Review Rules`）は直下の`AGENTS.md`に残している。2026-11-27に、ADR-0008（AWSとNeonからCloudflareへ移す）に合わせて、AWSとNeonの言葉をCloudflareの言葉に直した。

## レビュー

### 誰が見るか

- レビュアーは全員、`main`にある`REVIEW.md`を読んで見る。何を重点的に見るかと、差分で当てる確認項目はそこに書く。レビュアーを増やして見落としを減らすのでなく、`REVIEW.md`を直して減らす（2026-11-18 ユーザーの判断）。
- 検査そのもの（`REVIEW.md`、`.github/workflows/`、`docs/tests/`の試験の観点、ハーネス）を変えるときは、アプリのコードと別のPRにする。変更が自分を判定する検査を書き換えられないようにするため。
- 設計の工程（ADR・データモデル・要件と設計書）は、承認の前にCodexで反例を探すレビュー（敵対的レビュー）をする。
- コードのPRは、Claude Code本人・`reviewer`・（条件を満たすとき）`security-reviewer`を並べて見る。DevinのPRはDevin Reviewにも見せる。
- Codexは、PRを開いたときに自動でレビューする。設定はリポジトリの外（Codexの設定）にあり、直下の`AGENTS.md`の「Code Review Rules」を読む。開いたときのレビューにメンションは要らない。次のときは、PRに`@codex review`とコメントして見直してもらう。
  - レビューの指摘を直してpushしたとき。PRのレベルは問わない。直しで別の不具合が入っていないかを見てもらうため。
  - 設計・ロジックを変えるpushをしたとき（指摘の直しでなくても）。
  - DevinなどボットのPRを開いたとき。CodexはボットのPRを自動でレビューしないため。
  - 文言・nitだけの直しでは頼まない。
- 見直しで新しい指摘が出たら、同じ手順で直して、もう一度頼む。同じ型の指摘がくり返し出るときは、場当たりに直さず原因を直す。
- マージ判断をユーザーへ渡す前に、L2 / L3のPRは現在headにCodexのレビューがあること、どのPRも現在headの完全SHAに対するClaudeの完了のコメントがあることを確かめる。短いSHAは完了の印にしない。

### 人がじっくり見る変更

間違えたときに戻しにくい変更は、人が差分を見る。すぐ戻せる変更は、Devin ReviewやCodexのレビューと、実在する検査に任せる。マージするかどうかは、これまでどおり人が判断する（`docs/agents/roles.md`のゲート）。

見る範囲は、触ったファイルで決める。説明に書いていなくても、ファイルが下の範囲なら人が見る。

根拠は`docs/reviews/human-review-sources.md`。

人が差分を見るのは、次である。2026-11-27にADR-0008でAWSとNeonをCloudflareに替えたので、各項目もCloudflareの言葉で書く。

- 認証と権限。Better Authのパスキーとセッション、`users.status`の確認、グループのメンバーであることの確認（`docs/architecture.md`、`docs/api.md`）。招待リンクを通らないログインだけでは、ユーザーは作られない。将来は`src/contexts/group/`と、VoidのAPIの置き場所`routes/`。
- お金を受け取る処理。いまは無い。PR/FAQの「やらないこと」に、決済と割り勘の精算がある。足すときは、その変更を人が見る。
- DBの構造を変える変更と、データを消す処理。D1へ流すdrizzle-kitのSQL。テーブル定義は各文脈の`infrastructure/`（例は`src/contexts/group/infrastructure/`）。SQLのファイルは`src/contexts/`の外に置く（ADR-0004の決定2）。SQLを置くディレクトリの名前は、まだ決めていない。D1で過去の時点に戻せるのは、無料プランの7日までである（ADR-0008）。戻すときの手順は`docs/data-model.md`の「D1を過去の時点に戻したとき」。解散・退会・外すは、将来`src/usecases/disband-group/`、`src/usecases/withdraw-user/`と、Queuesの受け手（処理の分け方はADR-0002の決定5、決定6、動かし方はデータモデルのR23）。
- 個人の情報。`groups.users`の表示名、Better Authのユーザーとパスキー、通知先の`endpoint`（`docs/data-model.md`）。ログに名前、メールアドレス、内容を書かない決まりも、ここである。
- CI、デプロイ、インフラの設定。`.github/workflows/`には、Claudeのレビュー（`claude-code-review.yml`）と品質確認（`ci.yml`）がある。品質確認はPRと`main`へのpushで動く。ハーネス試験、lint（文脈の境界を含む）、型チェック、Vitestを実行する。対象があればPWAをビルドし、成果物に試験専用のコードや値が入っていないかも調べる。本番には配置しない。Voidの設定と、D1・R2・Queues・Cronの定義、無料プランの上限とR2の費用（データモデルのR25）も、ここに含める。`infra/terraform/`のAWS向けのファイルは、作り直しの計画で片づける。
- 秘密の値の置き方。Web PushのVAPIDの秘密鍵、招待リンクのトークンを作る値、Better Authの秘密の値は、Workersのsecretに置く（ADR-0008。招待リンクの値はADR-0005）。CIが使う`CLOUDFLARE_API_TOKEN`はGitHubのSecretsに置く。VAPIDの公開鍵は配置のときに置く公開の設定ファイルで画面に渡し、秘密の値ではない（`docs/api.md`）。値そのものは、リポジトリにも設定ファイルにもPRにも書かない。secretの名前や、トークンの権限を変える変更を人が見る。

設計資料や説明の誤字、画面の見た目だけの調整は、すぐ戻せる。人が差分をじっくり見なくてよい。下の表の「要約で足りる」に入れる。上の範囲のファイルを触る変更は、中身が誤字だけでも人が見る。誤字で「要約で足りる」になるのは、その範囲の外の設計資料や説明だけである。検査そのもの（`REVIEW.md`、`.github/workflows/`、`docs/tests/`の試験の観点、ハーネス、直下の`AGENTS.md`、このファイル）を変えるときは、下の表のとおり人が差分を見る。

上の範囲を含むPRは、説明の冒頭（雛形の「重点的に見てほしいところ」）に、どの範囲を触ったかを書く。その変更は、誤字や見た目と混ぜず、小さいPRに分ける。分けたあとも、上の範囲を触ったことは各PRの冒頭に書く。

下の表の「必ず見る」は、この節と合わせて使う。この節の範囲は「必ず見る」に入れる。リマインドの送信時刻と再送、設計書との食い違い、検査そのものの変更と試験の削除・assertを弱めた箇所も、表のとおり人が差分を見る。

### ユーザーが読むところ（重みづけ）

ユーザーは重大なところを中心に読む。上の「人がじっくり見る変更」に当たる差分は、「必ず見る」に入れる。Claude CodeはPRの説明の先頭と、完了のコメントの本文の先頭（`review-devin-pr`の完了の印`<!-- claude-review-done … -->`の直後）に「重点的に見てほしいところ」を書き、次の2段に分ける。

| 段 | 何が入るか | ユーザーの読み方 |
| --- | --- | --- |
| 必ず見る | DBの表とmigration、グループのメンバー確認などの認可とBetter Auth、データを消す処理（解散・退会・外す）、リマインドの送信時刻と再送、IaC・費用・秘密の値、設計書との食い違いの判断、検査そのものの変更と試験の削除・assertを弱めた箇所 | 差分を読む |
| 要約で足りる | それ以外 | Claudeの要約と完了のコメントを見てマージする |

設計書と実装計画（L2 / L3）は中身を読む。

### CIと指摘の追跡（2026-11-10 ユーザーの指示）

- PRを出したClaude Code（またはDevin）は、マージか閉じるまで、そのPRのCIとレビューのコメントを自分で追い、直す。ユーザーに見張りを頼まない。
- CIが落ちたら、このPRの変更が原因かを確かめ、原因なら直してpushする。`main`でも落ちるなど原因がほかにあるときは、その旨をPRに1回書き、ユーザーに伝える。試験を飛ばしたり、assertを弱めたりして通さない。
- 同じ検査を3回直しても落ちるときは、止めてユーザーに渡す。何を試して、どこで落ちているかを書く（2026-11-18 ユーザーの判断）。
- 通ったり落ちたりする試験は、再実行・待ち時間の追加・スキップで通さない。原因を調べても分からなければ、その試験を消してよい。消すときは、理由と、何を確かめなくなったかをIssueに残し、PRの「必ず見る」に入れる（2026-11-18 ユーザーの判断）。
- 人の指摘と、Claude Codeが追う指摘（Codex、Devin Review、`reviewer`を含む）には、直したか、直さない理由を各スレッドに返し、直したスレッドは解決にする。Devinが自分のPRでボットの指摘を直すときだけ、スレッドごとに長い返信を書かない。1回の直しのあと、PRに要約を1件書く。直したもの、飛ばしたものと理由、著者への問いをそこに入れる。セキュリティの中身と、セキュリティ指摘があることも、その要約に書かない。手順は`.agents/skills/devin-workflow/SKILL.md`の「4.5」。設計判断が要る指摘とセキュリティの指摘は、直す前にユーザーに渡す。
- ユーザーに知らせるのは、追跡が一回りして結果が出たとき、止まったとき、判断が要るときだけ。

### 指摘の扱い

- コードレビューの指摘タイトル・本文・レビュー要約は日本語で書く。コード、識別子、ファイルパス、API名、優先度表記（`[P1]`など）は原文のまま保つ。
- 各バグを、それが起こる頻度と深刻さの両方で1から10まで評価する。各スコアと積、発生条件と評価の根拠を指摘に添える。頻度は現在の仕様・利用経路を基準に、1は例外的な条件でのみ起きるもの、5は通常利用の一部で繰り返し起きるもの、10は対象の操作でほぼ毎回起きるものとする。深刻さは1〜4を軽微な表示・操作上の不便、5〜7を主要な操作の失敗や誤った結果、8〜10を情報漏えい・権限逸脱・データ消失・リマインドの取りこぼしなどとする。発生頻度と、指摘が正しいという確信度を混同しない。
- 頻度と深刻さの積が5未満なら、Issueとして登録し、今回のコードはそのままにする。積が5以上でも自動で修正対象にせず、再現条件と今回の変更範囲を確かめる。セキュリティに関わる指摘は非公開で扱う手順を優先する。
- DevinのPRへの`must`の指摘（と同じ回の`nit`）は自動でPRに投稿する。自動の投稿は2回まで。超えたらユーザーに渡す。セキュリティ指摘と設計判断が要る指摘は投稿せず、ユーザーに渡す。手順は`.claude/skills/review-devin-pr/SKILL.md`。
