# 作業分担

もとはリポジトリ直下の`AGENTS.md`の「作業分担」。中身は移しただけで、決まりは変えていない。

## 作業分担（AI駆動開発）

AIが実装し、ユーザーは要件提示・設計判断・レビュー・マージを担う。

- 既定でAIが設計案の提示から実装・テスト・PR作成まで、このセッションの一つのループで行う。ただしL2 / L3の実装計画から先は、`docs/agents/how-we-work.md`のとおりDevinに委譲する。設計・計画・実装はスキルを読んで進め、子エージェントに分けない。検証（`reviewer`、条件を満たすとき`security-reviewer`）と広い探索（`Explore`）だけ別の文脈に渡す。手順は`develop-feature`スキル。
- L2 / L3では設計書（`docs/designs/`）をユーザーが承認してから実装に入る。L0 / L1は承認なしで進める。
- 誰も求めていない珍しいケースや将来のケースのために設計しない。
- L2 / L3と設計の工程の問いと答え・選ばなかった理由は`docs/discussions/<機能名や工程>.md`（論点の記録）に、工程の状態は`<機能名>.progress.json`に残す（`docs/discussions/README.md`）。Claude Codeは問いと設計の承認依頼を、確認のページ（claude.aiの非公開のページ）で出す。推奨と違う答えが出たら、理由を一言聞いて記録する。
- 技術スタック・アーキテクチャなどADR級の決定はAIが候補と比較を示し、決定はユーザーが行う。
- `main`へ直接コミットしない。変更は作業ブランチ → PR。PRは積み上げず、`main`から切る。pushの前に、そのPRがマージ済みでないかを確かめる。破壊的操作（履歴改変・データ削除・本番操作）は事前確認する。
- 実装完了の報告には「何を・なぜそう設計したか・別解との比較」を含める。L2 / L3は必須、L1は3行以内の要約、L0は省略する。
- ユーザーへの説明では、工程の番号・試験の観点IDだけで物事を指さない。用語集の言葉で書き、番号は必要なら括弧で添える。

人が止まって判断するゲートは次のとおり。AIはゲートの手前まで進めてよい。

| ゲート | いつ | 誰が決めるか |
| --- | --- | --- |
| 工程の成果物とADRの承認 | 次の工程の前 | ユーザー |
| L2 / L3の設計承認 | 実装開始前 | ユーザー |
| ADR級の決定（スタック・アーキテクチャ・後方互換） | 採用前 | ユーザー（AIは比較まで） |
| PRのマージ | 品質確認後 | ユーザー |
| 破壊的操作 | 実行前 | ユーザー |

## ツールごとの入口

もとは`AGENTS.md`の「ツールごとの入口」。Claude Codeは`.claude/AGENTS.md`、Devinは`.agents/AGENTS.md`。

- Codex: 設計の敵対的レビューと、PRのレビュー（`docs/agents/review.md`）を担う。実装はしない。レビューでコマンドを動かすときも、`docs/agents/command-scope.md`に従う。
- Cursor: ユーザーが「必ず見る」差分を読み、手で直すときに使う。AIの役割（実装・レビュー）は持たせない（2026-11-12 ユーザーの判断）。
