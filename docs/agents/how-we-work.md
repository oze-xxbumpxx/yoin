もとはリポジトリ直下の`AGENTS.md`の「進め方の決まり」。中身は移しただけで、決まりは変えていない。

## 進め方の決まり（2026-11-10 ユーザーの判断）

- 工程6を閉じてから実装に入る。最初の実装は、登録からグループ・公演を経て、チケットのリマインドがiPhoneに届くまでを通す1本にし、本番と同じ構成の環境で動かす。この1本はL3の機能として、要件・設計・実装計画・試験計画を書いてから始める。
- 実装は最初からDevinに委譲する。土台（IaC・CI・デプロイ・Cognito・Web Push）も委譲する。そのため、道具の選択は委譲の前に工程4〜6で決め切る。
- L2 / L3の機能は、要件定義書と設計書をClaude Codeが書き、実装計画・試験計画・実装はDevinに委譲する。Claude CodeはDevinのPRのレビューに回る（2026-11-24 ユーザーの判断。2026-11-23からは設計書もDevinが書いていた。最初の1本の設計書はDevinが書いた）。設計書の承認がユーザーのゲートであることは変わらない。実装計画・試験計画を頼むIssueは、承認済みの設計書を起点にClaude Codeが作る。`delegation.mjs open-task`はマージ済みの実装計画を読むので、実装のタスクの委譲だけに使う。
- Devinは、手元のDevin CLIを基本にする（2026-11-11 ユーザーの判断）。並行で進められるタスクは並行で渡す。
  - 委譲はDevin CLIのSWE-2.1で起動する（2026-11-24 ユーザーの判断）。`--model`に渡す名前は、Macで`devin models list`に出るSWE-2.1の名前をそのまま使う。effortは、タスクの実装の難しさで選び、計画のタスクごとに書く。
  - Devin CLIが、自分では実装できないと判断したときは、Devin CLIの中からDevin Cloudを呼び出して渡す。Claude Codeが直接Cloudを起動することはしない。
  - 並行で渡すタスクは、触るファイルが重ならないように分ける。実装計画の分け方の表に、タスクごとの主に触るファイルとeffortを書く（tomotabiでは、ファイルで分けて3本を同時に進めても衝突しなかった）。
  - 手元のDevin CLIは、専用のクローン1つにつき1本だけ動かす。
  - Devin CLIからCloudを呼び出せることは、最初の委譲の前に1回確かめる。確かめるまでは、CLIで実装できないタスクはユーザーに渡す。
  - DevinのPRのレビューと委譲の記録は、CLIでもCloudでも同じ手順（`review-devin-pr`）にする。
- 最初の委譲の前に、Cookpitの配布物を更新して、tomotabiで育てたハーネスを取り込む。
- ハーネスは、困ったときにその都度作る。
- 設計の問い・ADR・要件定義書・設計書と、設計書の承認依頼はclaude.aiのプロジェクトで、実装・Devinへの委譲・PRのレビューはMacのClaude Codeで進める。実装計画・試験計画を書くのはDevin（上の決まり）。手元のDevinはMacでしか起動できないため。
- migrationはデプロイの流れに入れる。手で流す手順は作らない（tomotabiでは本番にmigrationが流れず、機能が動かなかった）。
- E2Eは最初の1本から入れる。グループは複数人が前提なので、2人をブラウザのcontext 2つで動かす。Web Pushは、ホーム画面に追加したiPhoneのPWAで確かめる。
- 結合検証環境で見る項目には、見るのに要るデータと、それを誰が作るかを書く。
- 最初の1本の実装計画に、アプリを起動してE2Eの流れを操作する確かめのスキルを作るタスクを入れる。Devinが作り、Claude CodeとDevinの両方がPRを出す前に使う（2026-11-18 ユーザーの判断。`docs/discussions/verification-loop.md`）。
- コアの文脈の決まり（チケットの申込の状態の移り方など）、リマインドの送信と再送、解散などの削除ジョブは、例を書く試験に加えて、fast-checkで入力を作らせて「決して破れない決まり」と「2回流しても同じ」を確かめる（2026-11-18 ユーザーの判断）。
