# 論点の記録: 最初の1本をCloudflareとパスキーに合わせる

- 機能名: first-slice-cloudflare
- 確認のページ: https://claude.ai/artifact/DV2E6bekmN9RvfzoLy2GcZ
- 進み具合: docs/discussions/first-slice-cloudflare.progress.json

## 背景

最初の1本（登録からチケットのリマインドがiPhoneに届くまで）の要件定義書と設計書は、AWS・Neon・Cognitoのメールのコードを前提に書いてある。ADR-0008（PR #96）とデータモデルの直し（PR #97）で、Cloudflareの無料プラン、D1、Void、Better Authのパスキーに替えた。要件定義書と設計書を書き直す前に、ADR-0008で「最初の1本の設計書で決める」と残した点と、メールをやめて変わる点を決めてもらう。

## 前提

- 費用は0円にする。月5ドルのWorkers Paidも使わない（2026-11-27、大関さん）。個人開発で世に出さず、高品質は求めない。
- ログインはパスキーで、メールは送らない（ADR-0008の決定5）。招待リンクを通らないログインだけでユーザーを作らない決まりは変えない。
- パスキーは登録したときのドメインに結び付く。あとでドメインを替えると、登録済みのパスキーがすべて使えなくなる（ADR-0008の決定5）。
- D1を過去の時点に戻したあと、届いたか確かめられないリマインドは`held`にし、オーナーが1件ずつ決める（データモデルR22、PR #97で大関さんが受け入れた）。
- 要件F-01（結合検証と本番を分ける）は、AWSのときに大関さんが決めた（2026-11-25）。
- ClaudeとDevinはCloudflareのアカウントにつながない。本番での確かめは大関さんが行う。

## 調べた事実

2026-11-27に、npmのvoid 1.12.2に入っている文書を読んだ。動かしてはいない。

- `void deploy --platform cloudflare`（自分のCloudflareアカウントへの配置）では、名前付きの環境（stagingなど）は使えない。WorkerとアカウントはVoidの設定（`void.config.ts`）と`void.lock.json`で1つに決まる。
- Voidは`workers.dev`の名前（`<Workerの名前>.<アカウントの名前>.workers.dev`）に配置できる。独自ドメインも付けられる。
- `workers.dev`の名前で動くアプリが置いたクッキーは、同じアカウントの`workers.dev`の名前で動くほかのWorkerにも届く（Voidの文書）。結合検証と本番を同じアカウントに置くと、クッキーの名前を分ける必要がある。
- Cronは1アカウント5個まで（無料プラン）。D1を過去の時点に戻すのは7日まで。
- Better Authは、ユーザーを作る前に呼ぶつなぎ目（auth hooks）を持ち、Voidの`auth.ts`で書ける。

## 論点

### 結合検証と本番を分けるか

<!-- id: fs-env -->

- 工程: 要件
- 種類: 設計
- 優先度: 高
- 状態: 回答待ち
- なぜ今: 要件F-01・F-02（結合検証で確かめてから本番に出す）の書き方と、ドメインの数が決まる。Voidは1つの設定で1つの配置先しか持てない。
- 根拠: Voidの文書`reference/cli/deploy.md`（Named environments: Unavailable）、`guide/auth.md`（workers.devのクッキー）、要件定義書F-01・F-02
- 選択肢:
  - A) 本番だけにする。PRでは手元のVoidの開発サーバーとCIの試験で確かめ、iPhoneへの通知は本番で確かめる
    - 利点: 配置先・ドメイン・パスキーが1組で済む。CIの承認の段も要らない。Cronは1個
    - 欠点: マイグレーションの誤りが、確かめる前に本番のデータに当たる。D1を戻せるのは7日まで
  - B) Cloudflareのアカウントを2つ作る（どちらも無料）
    - 利点: 資源・secret・クッキー・無料の上限が完全に分かれる
    - 欠点: アカウントとAPIトークンが2組になる。大関さんの管理の手間が倍になる
  - C) 1つのアカウントに2組置く（Workerの名前を分け、Voidの設定と`void.lock.json`を2つ持つ）
    - 利点: アカウントは1つのまま、本番の前に確かめられる
    - 欠点: Voidが想定していない使い方で、設定の切り替えを自分たちで作る。クッキーの名前を分ける。無料の上限（1日10万リクエスト、D1の書き込み10万行）を2組で分け合う
- 推奨: A（10人で使う個人開発なら、1組のほうが手間とつまずく所が少ない。マイグレーションはCIで手元のD1に流して確かめ、壊れたら7日以内に戻せる）

### 使うドメインをどれにするか

<!-- id: fs-domain -->

- 工程: 要件
- 種類: 設計
- 優先度: 高
- 状態: 回答待ち
- なぜ今: パスキーは最初に登録したドメインに結び付く。あとで替えると、全員がパスキーを登録し直すことになる。
- 根拠: ADR-0008の決定5、Voidの文書`guide/platform/installation/domains`
- 選択肢:
  - A) `workers.dev`の名前を使う（例: `yoin.<アカウントの名前>.workers.dev`）
    - 利点: 0円。設定が要らない
    - 欠点: Workerの名前やアカウントの名前を替えると、パスキーが使えなくなる。URLが長い
  - B) 独自ドメインを買って使う
    - 利点: URLが短い。Cloudflareの中で配置先を替えてもドメインはそのまま
    - 欠点: 年に1,500円ほどかかる（推測）。費用0円の方針から外れる
- 推奨: A（費用0円の方針に合う。Workerの名前とアカウントの名前は、決めたあと替えないと設計書に書く）

### 最初のオーナーをどう作るか

<!-- id: fs-owner-setup -->

- 工程: 要件
- 種類: アプリの決まり
- 優先度: 高
- 状態: 回答待ち
- なぜ今: 要件F-03は、デプロイの流れでCognitoのユーザーをメールアドレスで作る形だった。パスキーはサーバーで作れず、本人の端末で登録するしかない。
- 根拠: 要件定義書F-03・F-07、AGENTS.md「認可」
- 選択肢:
  - A) 大関さんがWorkersのsecretに「はじめの合言葉」を置く。オーナーがいないあいだだけ、はじめの画面で合言葉を入れるとパスキーを登録してオーナーになれる
    - 利点: 招待を通らないユーザーは、この1回だけで、合言葉を知る人しかなれない。オーナーができたら画面は閉じる
    - 欠点: 画面が1つ増える。合言葉は大関さんが`void secret put`で置く
  - B) 最初にパスキーを登録した人をオーナーにする
    - 利点: 何も置かなくてよい
    - 欠点: 公開してから大関さんが登録するまでのあいだに、URLを知った他人がオーナーになれる
- 推奨: A（招待を通らない登録を、合言葉を知る1人だけに絞れる）

### パスキーの端末をすべてなくした人をどう戻すか

<!-- id: fs-recover -->

- 工程: 要件
- 種類: アプリの決まり
- 優先度: 高
- 状態: 回答待ち
- なぜ今: メールが無いので、本人だけでは戻せない。ADR-0008で「最初の1本の設計書を直すときに決める」とした。
- 根拠: ADR-0008の決定5と「残った問い」
- 選択肢:
  - A) オーナーがS-21（メンバーと招待）から、その人の「戻すリンク」を出す。本人が開いてパスキーを登録すると、前のアカウントに戻る。古いパスキーは消す
    - 利点: 記録・申込・リマインドがそのまま残る
    - 欠点: リンクが漏れると、ほかの人がその人になれる。1回だけ、24時間で切れる、オーナーだけが出せる、の3つで絞る。画面とAPIが1つずつ増える
  - B) オーナーが招待を出し直し、新しいアカウントで入り直す
    - 利点: 新しく作るものが無い
    - 欠点: 前の申込・参戦記録・リマインドは前のアカウントに残り、本人は見られない
- 推奨: A（iPhoneの買い替えでiCloudキーチェーンが移らないことはある。そのたびに記録を失うのは困る）

### 送れなかったリマインドを誰に知らせるか

<!-- id: fs-failed-notice -->

- 工程: 要件
- 種類: アプリの決まり
- 優先度: 中
- 状態: 回答待ち
- なぜ今: いまの要件E-10・F-18は、送れなかったときにAWSのキュー（C-4）に入れ、オーナーにメールで知らせる。メールを送らなくなったので、知らせ方を決め直す。
- 根拠: 要件定義書E-10・F-18、設計書「ログと監視」
- 選択肢:
  - A) 本人にだけ知らせる。ホームの帯とS-23の「送れなかった」の印で出す（いまもある）
    - 利点: 新しく作るものが無い。0円
    - 欠点: オーナーは、メンバーに届いていないことに気づけない
  - B) Aに加えて、オーナーのS-21に「送れなかった端末がある人」の印を出す
    - 利点: オーナーが気づいて本人に声をかけられる
    - 欠点: 画面とAPIに少し足す。ほかの人の通知の状態をオーナーが見ることになる
- 推奨: A（本人が帯で気づけば足りる。Cronが止まったなど全体の失敗は、大関さんがCloudflareの管理画面で見る）

### DBを戻したあとの`held`のリマインドを、オーナーがどこで決めるか

<!-- id: fs-held -->

- 工程: 要件
- 種類: 画面
- 優先度: 低
- 状態: 回答待ち
- なぜ今: データモデルR22で、届いたか確かめられないリマインドは`held`にしてオーナーが1件ずつ決めると決めた。決める場所が要件にも設計にも無い。手でSQLを流さない決まりもある。
- 根拠: `docs/data-model.md`の「D1を過去の時点に戻したとき」、AGENTS.md「データの消失」
- 選択肢:
  - A) オーナーの画面に「確かめが要るリマインド」の一覧を出し、1件ずつ「送る」「送らない」を押す。`held`が無いときは出さない
    - 利点: 手でSQLを流さずに済む。データモデルのとおりに動く
    - 欠点: めったに使わない画面を1つ作る
  - B) 最初の1本では作らない。戻すことになったら、そのとき作る
    - 利点: いまの作業が減る
    - 欠点: 戻したあとリマインドが止まったままになり、急いで作ることになる
- 推奨: A（D1を戻すのは事故のときで、そのときに画面を作る余裕は無い。一覧と2つのボタンだけにする）
